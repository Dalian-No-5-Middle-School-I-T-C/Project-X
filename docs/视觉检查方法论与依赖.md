# Project-X 视觉检查方法论与依赖清单

> 适用对象：Project-X（答题卡设计 / OMR 阅卷 / 成绩分析系统）的 UI 与端到端流程验证。
> 本文说明「视觉闭环验证」的工作方式、阶段划分、以及运行它所需的全部依赖与精确版本。
> 配套计划：`.workbuddy/plans/E2E-FLOW-VERIFICATION-2026-08-07.md`

---

## 1. 概述

「视觉检查」不是跑通单测或 typecheck 就结束，而是**用真实浏览器实际走完业务操作并逐页截图留证**，再与设计基准对照，区分「数据问题」与「代码 bug」。

核心主张：typecheck / build 全绿 ≠ UI 完成。任何页面改动或新功能在 sign-off 之前，必须经过本门——否则只能说「代码编译过了」，不能说「界面能用、用户遇不到 bug」。

本方法既能验证**单个页面/组件**（迁移或 bug 修复后自验），也能验证**整条业务主链路**（建卡 → 扫描 → 阅卷 → 出分 → 查分）以及**全部已上线功能**（师生管理、大考组、成绩分析、背景图、备份恢复等）。

## 2. 方法论与铁律

### 2.1 铁律

1. **证据优先**：每一步的结论 = Playwright 截图 + 关键 UI 文本/状态断言。任何「未截图即宣称通过」视为违规。
2. **真实驱动**：用浏览器真实点击、填表、上传文件，而非仅调 API 或只读 DOM。
3. **对照基准**：截图与设计锚点对照（`design/demo/demo.html`、`design/designer-sandbox.html`、`design/DESIGN-SYSTEM.md`、`design/tokens/tokens.css`），不凭记忆判断「和 demo 一样」。
4. **区分问题性质**：
   - **数据问题（非 bug）**：空考试、空卡、占位科目导致的 EmptyState，用有数据的考试对照证明代码正确。
   - **代码 bug（阻塞）**：对照 demo 发现的真实视觉偏差（多余边框、错位、颜色错、暗色不可读）→ 记为真问题，回头修后重跑。
5. **HMR 滞后陷阱**：Tailwind utility + `@layer` 重排时 Vite HMR 常不传播 CSS 重建。截图/让用户验证前必须 **Ctrl+Shift+R hard reload**，否则会误判「已修好」。

### 2.2 检查流程（通用）

```
起服务 → 登录(含强制改密) → 导入演示数据
   → 逐阶段驱动浏览器执行操作并截图（亮+暗各一套）
   → 读取截图，对照设计基准逐项核对
   → 输出《视觉闭环核验报告》+《端到端流程验证报告》
```

### 2.3 视口与主题

- 视口 `1600×900`（16:9），`deviceScaleFactor: 2`，`locale: zh-CN`，`timezoneId: Asia/Shanghai`。
- 主题通过 `document.documentElement.setAttribute("data-theme", "light"|"dark")` 切换，亮/暗各拍一套，验证暗色可读、无对比塌陷。

## 6. 脚本扩展方法（`scripts/screenshot.mjs` 的 SPECS）

验证新页面只需编辑 `SPECS` 数组，无需改驱动逻辑：

```js
{
  name: "my-page",
  label: "我的页面（演示-物理）",
  drill: { rowText: "演示-物理" },   // 从列表点行进详情；或 path: "/xxx" 直接导航
  steps: [
    { clickSeg: "大考" },            // 点 SegmentedControl（text-is 精确）
    { clickTab: "题目分析" },        // 点 role=tab
    { clickBtn: "新建大考" },        // 点 button（text-is 优先，回退 contains）
    { clickRow: "演示-网阅测试" },   // 点含文本的 table 行
    { clickRowFirst: true },         // 点首个 table 行
    { clickCardFirst: true },        // 设计画廊点第一张卡片
    { ensureFillBlank: true },       // 进入填空块编辑器（无则添加）
    { openAccountMenu: true },       // 展开 AppRailFooter 账号菜单
    { waitSel: "button:text-is('大考')", timeout: 8000 },
    { sleep: 1200 },
  ],
  wait: "[role='tablist']",          // 截图前等待的关键选择器
  waitTimeoutMs: 12000,
  studentOnly: true,                 // 仅以学生身份跑（脚本会自动 loginAs 学生）
}
```

**交互型 E2E（建卡 / 上传 / 打分）** 在 `screenshot.mjs` 之外另写专用脚本：复用其 `loginIfNeeded` / `handleForcedChange` / `loginAs` / `shoot` 逻辑，叠加 `page.setInputFiles()` 上传扫描图、`page.fill()` 填表单、`page.click()` 触发保存/提交等操作，并对每个关键步骤 `shoot()` 留证。

## 7. 诚实边界（环境未测项，非代码缺陷）

以下三项本机无法真实跑通，已在计划中标注，不削弱业务主链路结论：

| 项目 | 原因 | 处理方式 |
|---|---|---|
| TWAIN 物理直扫（按「开始扫描」按钮真扫） | 无扫描仪硬件接入 | 验证 ScannerWorkspace/ScannerPanel UI 可渲染、文件导入替代路径可用、无硬件时提示优雅；标注「硬件未测」 |
| C++ OMR 对「已填涂答题卡」高保真识别 | 仓库无已填涂原图（只有真实扫描件 + 网阅占位图） | 用现有真实扫描 jpg 试跑链路；另用空白图强制触发 STUDENT_ID_MISSING / RECOGNITION_FAILED 异常路径 |
| 原卷上传 + AI 知识点 | 需外部 LLM key | 验证面板可渲染、上传不崩；AI 打点标注「需 key 未测」 |
