## 概要

此问题由本次修改引入。应将两处新增的 indeterminate 字面量替换为现有 ObjectiveMode 值 indefinite。尤其是在 objective.mode 为 multiple 或 indefinite 时，删除条件应当保留评分规则。

本次提交在两处引入字符串 indeterminate，但 ObjectiveMode 定义的值是 indefinite。因此，题型变更处理函数中的比较会触发 TypeScript 错误 TS2367，阻止仓库正常的 npm run build 流程，因为该流程执行 tsc --noEmit。如果绕过类型检查，选择有效的 indefinite 模式会使第 2382 行的两个比较都为真，进而删除每道题的 scoringRule。判分实现依赖该规则授予部分分数，因此后续判分可能静默地为所有受影响题目及学生计为零分或采用兜底分数。同一个拼写错误还会使不定项选择题块自动生成的标题使用通用客观题名称。这属于数据完整性及发布质量缺陷，但没有越过安全边界：触发需要已获授权的答题卡编辑者修改判分配置，而该操作者本来就有权改变这些规则。

## 攻击路径分析

在策略排除之前，已确认的中等数据完整性影响与低发生可能性，按矩阵得到低严重性。最终策略阶段适用受保护写入路径和仅特权用户可执行的排除规则：在生产威胁模型下，触发持久化需要 grade:write，而该操作者已经有权直接修改或移除受影响的判分规则。没有验证出提权、授权绕过或跨边界能力增益。默认关闭认证的兼容模式也不能使该问题变为可报告，因为该模式本来就允许任意答题卡写入，并且不属于所假设的加固生产配置。因此，该问题应作为阻断发布的判分正确性缺陷修复，但在安全漏洞层面忽略。

### 路径

已授权教师／编辑者选择 indefinite 模式 → 正常设计器下拉框事件触发 → App.tsx 的拼写错误将 indefinite 视为不受支持的模式 → 执行错误的 indeterminate 比较 → 每道题的 scoringRule 被删除 → 1.2 秒自动保存序列化被修改的答题卡 → 自动保存 PUT /api/cards/:cardId 通过 grade:write 检查 → 执行已授权持久化 → CardRepository 将 scoring_rule_json 保存为 NULL → 生产判分读取缺失的规则 → 判分或重算使用零分或旧版兜底规则。

规范的 ObjectiveMode 为 single、multiple 或 indefinite，但 App.tsx 的自动标题映射和题块模式变更处理函数都使用 indeterminate。在仅转译或其他不进行类型检查的执行方式中，已授权编辑者选择 indefinite 会导致处理函数删除每道题的 scoringRule。自动保存随后把答题卡提交至答题卡 API，CardRepository 将缺失规则保存为 NULL。生产判分允许 multiple 和 indefinite 模式获得部分分数，但当单题规则和旧版兜底规则均不存在时，会退回错选／多选分数，通常为零。提供的可执行复现证明，部分分数从 1 变为 0。反对运行时影响的最强证据是 npm run build 会先执行 tsc，并以 TS2367 拒绝该比较，因此无法用此提交完成正常发布构建。反对安全可报告性的最强证据是 grade:write 检查：现实触发者本来就有权修改这些评分规则，没有证明低权限攻击或额外权限收益。因此，这是已确认的产品正确性和判分完整性缺陷，但作为安全发现被排除。

## 发生可能性

低（Low）。对于已授权编辑者，界面触发路径很直接；提供的可执行复现确认了规则修改和分数变化。不过，运行时利用需要操作者拥有受保护的成绩写入能力、答题卡存在相关部分给分规则、修改被持久化后再执行判分，以及运行路径绕过正常的类型检查构建。普通构建会在发布前拒绝该提交，也没有建立现实可行的低权限攻击路径。这些条件使安全利用的可能性较低。

## 影响程度

中（Medium）。如果存在缺陷的前端实际运行并保存修改，删除部分给分规则会改变多名学生的客观题成绩及重算总分，因此正确性影响具有实质性。该影响并非普遍发生，因为旧版 multipleScoring 规则可能提供兜底行为；标题拼写错误本身则只是外观问题。从安全角度看，相关操作者已经有权改变同一判分配置，因此影响属于数据完整性和正确性，而非授权或信任边界突破。

- 运行时影响需要仅转译的开发流程、包含缺陷的预构建产物，或其他绕过正常类型检查构建的路径。

## 控制措施

- 正常 npm run build 先执行 tsc --noEmit，并因无效比较处的 TS2367 失败，从而限制发布暴露。
- 启用 PROJECTX_AUTH_ENFORCE 时，非 GET 的 /api/cards 请求要求认证和 grade:write。
- 默认权限映射不向学生授予答题卡或成绩写入权限。
- 设计界面受 design 变体及 CARD_READ 权限限制。
- 服务在持久化前规范化客观题，但不会重建已删除的单题评分规则。
- 对部分旧答题卡，旧版题块级 multipleScoring 规则可能减轻分数影响。
- 服务直接绑定 127.0.0.1，不过所提供的生产模型允许通过代理或隧道对外暴露。
- 此问题不涉及秘密访问、代码执行、身份接管或可执行代码接收点。

## 盲点

- 可执行复现复制了那一小段内联 React 修改逻辑，没有驱动真实浏览器或完整的 HTTP／数据库集成。
- 没有已提交的反向代理、Cloudflare Tunnel 或负载均衡器清单来确定实际部署的网络暴露。
- 静态仓库证据无法确定，是否有生产或分发的预构建包在正常构建失败的情况下仍包含该提交。
- 无法从仓库文件确定实际受影响的答题卡、题目、考试或学生数量。
- 如果部署故意保持 PROJECTX_AUTH_ENFORCE 关闭，答题卡写入将无需认证；但这一更广泛的配置弱点与拼写错误不同，也不会产生该拼写错误特有的额外能力。
