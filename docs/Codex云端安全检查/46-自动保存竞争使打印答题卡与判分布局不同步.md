# 46 自动保存竞争使打印答题卡与判分布局不同步

## 概要

本次提交加入异步自动保存，并把直接 PDF 链接替换为“先保存、再导出”的流程，但没有等待保存期间产生的新编辑，因此引入了竞争条件。本地修订检查能防止旧响应覆盖 React 状态，却不能阻止 exportPdfForCurrentCard 使用该旧响应，也无法保证随后打开的 PDF 对应最终修订。

PDF 导出会捕获答题卡快照及修订号，将其发送到服务端，并无条件返回该已保存快照。如果教师在请求尚未完成时编辑答题卡，persistCardSnapshot 虽然会检测到较新的本地修订，却只安排另一次自动保存，仍然返回较旧的服务端响应。exportPdfForCurrentCard 随即验证该旧响应并打开其 PDF 地址，而较新修订约在 1.2 秒后才保存。PDF 保存期间，编辑器输入控件并未锁定，因此普通使用就能触发这一竞争，尤其是在通过远程反向代理访问时。结果可能是打印答题卡采用旧题号、分值字段或几何布局，而服务端随后保留新答题卡，并使用重建后的新布局扫描和判分。这可能静默地导致整批答题卡识别或判分错误。导出路径应在导出完成前阻止编辑，或者持续保存直到 savedRevisionRef 等于 editRevisionRef，再生成绑定到该确切不可变修订的 PDF。

## 验证

1. 确认 PDF 发起的保存尚未完成时仍可编辑答题卡；编辑器输入没有被 isBusy 禁用。
2. 确认修订检查虽然检测到新修订，却不会等待其保存，而是把过时保存响应返回给导出流程。
3. 确认 PDF 地址没有绑定不可变修订，服务端渲染的是可变的已存储答题卡状态。
4. 通过真实 HTTP 保存和 PDF 接口复现，并确认打开的 PDF 包含修订 A，而延后的自动保存使服务端最终保留修订 B。
5. 尝试通过完整浏览器界面复现，再对布局不匹配的实体答题卡进行扫描和判分；由于缺少宿主机库，Electron 无法启动，实体判分也不在本次限定测试范围内。

## 证据注释

1. 保存逻辑检测到更新的编辑后会安排另一次自动保存，但仍向调用方返回较旧的已保存快照。
2. 强制保存操作只捕获当前快照和修订号，不会循环等待请求期间产生的所有编辑都被持久化。
3. PDF 导出立即验证并打开第一次保存返回的快照，即使 persistCardSnapshot 已经发现它过时。
4. PDF 保存期间仍然可以编辑；编辑会增加修订号，并通过新的 1.2 秒自动保存计时器延后持久化。

## 攻击路径分析

技术校准为高完整性影响乘以中等发生可能性，按所提供矩阵得到中等严重性。之后单独进行的策略调整适用强制排除：已证明的路径要求教师或管理员本来就有权通过受保护写入流程修改同一共享答题卡，竞争条件没有赋予额外授权、身份、数据访问或修改能力。恶意的已授权教师不利用竞争，也可以直接保存或打印任一布局。没有证据证明学生、未认证用户、扫描端密钥或权限更低的教师能够触发受害者浏览器中的竞争或跨越信任边界。因此，尽管可执行验证证明了真实操作缺陷和潜在的批量判分后果，“仅特权用户可执行／没有新增权限”规则仍将最终可报告性从中等改为忽略。

### 路径

已授权教师位于答题卡设计界面 → 存在待保存编辑时点击 PDF → PDF 导出捕获修订 A，并发送 PUT /api/cards/:cardId → 网络响应尚未返回 → 教师在 PUT 响应途中创建修订 B → 响应返回前编辑修订号变化 → 修订检查安排 B 的自动保存，但返回过时的已保存对象 A → 导出使用过时返回值 → GET /api/cards/:cardId/pdf 渲染当前可变记录 A → 1.2 秒后的自动保存持久化 B → 延后保存写入 B 并替换服务端布局 → 打印修订和判分修订分离 → 打印的 A 可能按布局 B 进行扫描或判分。

可执行验证证明了生产答题卡流程中的真实竞争：修订 A 被渲染为一个 9,508 字节、包含五列学号栏的单面 PDF，而延后的自动保存使服务端最终保留具有九列学号栏的双面修订 B。客户端发现 A 已过时，却只是安排另一次自动保存，仍将 A 返回给导出流程。PDF 端点没有不可变修订查询，而是渲染当前数据库行。文档记载了公共反向代理部署，因此即使 Express 绑定回环地址，远程延迟仍可能扩大竞争窗口。现有控制会在内存中保留修订 B，最终将其持久化，校验分数，并禁用 PDF／保存按钮；但普通编辑器输入仍处于活动状态。最强反向证据是，唯一已证明的操作者是正在编辑其有权修改答题卡的已授权教师；没有学生、未认证用户或权限更低的教师因此获得访问或完整性修改权限。同一教师无需利用竞争，就能有意创建任一种答题卡状态。因此，这是已确认、可能产生严重后果的正确性和操作完整性缺陷，但按要求采用的受保护写入路径排除策略，不构成可报告的安全漏洞。

## 发生可能性

原栏标注高（High）。普通答题卡编辑即可触达该代码路径；远程代理延迟形成实际响应窗口，编辑控件保持可用，提供的可执行复现也使用真实端点和渲染流程生成了不同的旧版与最终版 PDF。不过，实际发生仍需要精确的编辑时机，以及后续未被发现的打印和判分；没有现实可行的低权限攻击路径或安全控制绕过。攻击向量为远程网络。

## 影响程度

高（High）。已证实的过时 PDF 在标题、单／双面设置和学号栏几何布局上均发生变化，而较新的服务端记录会重建不同判分布局。如果旧文档被整批打印，随后又按新布局扫描，完整性影响可能波及多名学生，需要重新扫描或重新判分。不过，没有演示实体扫描及实际误判分；较新的编辑也没有丢失，已授权操作者可以检查或重新生成 PDF。

## 假设条件

- 生产环境遵循所提供威胁模型，启用 PROJECTX_AUTH_ENFORCE，并将绑定回环地址的 Express 服务置于 HTTPS 反向代理之后。
- 操作者是获准设计和保存答题卡的已认证教师或管理员。
- 在后续自动保存更新服务端答题卡及判分布局之前，旧 PDF 已被打印或分发。
- 后续扫描或判分采用最新的可变答题卡定义，而不是与打印 PDF 匹配的不可变修订。

原文另列前提：

- 能访问已认证的答题卡设计会话，并有权编辑受影响答题卡。
- 答题卡存在未保存修改，随后执行 PDF 导出。
- 导出触发的 PUT 请求尚未结束时，再次编辑答题卡。
- 第一次 PUT 响应及 PDF GET，在 1.2 秒延后自动保存持久化第二次编辑之前完成。
- 未发现差异就使用过时 PDF 打印或分发。
- 后续按较新的服务端答题卡布局进行识别或判分。

## 控制措施

- 生产威胁模型假设 PROJECTX_AUTH_ENFORCE 已启用。
- 启用强制执行时，答题卡路由的角色访问控制拒绝未认证或权限不足的调用方。
- 设计界面有权限门槛。
- 修订比较防止旧响应覆盖较新的 React 状态。
- 延后的自动保存最终会持久化较新的编辑。
- 导出触发的保存忙碌期间，PDF 和手动保存按钮会被禁用。
- 分值校验可能要求用户确认，才打开存在警告的 PDF。
- PDF 响应使用 no-store 和 no-cache 头。
- 不涉及可执行代码接收点或秘密数据流。

## 盲点

- 提供的复现没有执行端到端实体扫描或批量判分，因此实际识别和成绩损坏仍是根据已证实的几何布局不匹配推断的。
- 竞争结果会随 refreshCards 的时机和网络调度变化；较晚的写入可能赶在可变 PDF 端点读取答题卡前完成。
- 无法获得实际部署配置，包括是否启用 PROJECTX_AUTH_ENFORCE，以及是否使用文档中的公共反向代理。
- 部署指南建议设置 HOST=0.0.0.0，但所检查的服务实现硬编码 127.0.0.1；因此公开暴露依赖独立反向代理。
- 验证因缺少宿主机图形界面库而无法直接自动化 Electron 浏览器，不过实际服务、PUT／PDF 端点、校验器和 PDF 渲染器都已被执行。
- 仓库证据未能证明低权限操作者可以在另一名用户的答题卡设计会话中强制制造所需的并发编辑。

  async function persistCardSnapshot(
    snapshot: AnswerCard,
    revision: number,
    source: "auto" | "manual" | "switch" | "pdf" = "manual"
  ): Promise<AnswerCard> {
    setAutoSaveState("saving");
    if (source !== "auto") {
      setIsBusy(true);
      setStatus(source === "pdf" ? "正在保存并检查分值..." : "正在保存答题卡...");
    }
    try {
      const saved = await fetchJson<AnswerCard>(`/api/cards/${snapshot.id}`, {
        method: "PUT",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify(snapshot)
      });

      const stillCurrent = latestCardRef.current?.id === snapshot.id;
      const noNewerEdits = editRevisionRef.current === revision;
      if (stillCurrent && noNewerEdits) {
        latestCardRef.current = saved;
        savedRevisionRef.current = revision;
        setCard(saved);
        setAutoSaveState("saved");
      } else if (stillCurrent) {
        scheduleAutoSave();
      }

      try {
        await refreshCards();
      } catch {
        // Saving succeeded; a stale sidebar timestamp is less important than preserving edits.
      }

      if (source === "auto") setStatus("已自动保存");
      else if (source === "pdf") setStatus("已保存，正在检查分值");
      else if (source === "switch") setStatus("已保存当前答题卡");
      else setStatus("已保存，并生成坐标布局数据");
      return saved;

  async function flushPendingCardSave(
    source: "auto" | "manual" | "switch" | "pdf" = "manual",
    force = false
  ): Promise<AnswerCard | null> {
    clearAutoSaveTimer();
    const snapshot = latestCardRef.current;
    if (!snapshot) return null;
    const revision = editRevisionRef.current;
    if (!force && revision === savedRevisionRef.current) return snapshot;
    return persistCardSnapshot(cloneCard(snapshot), revision, source);
