## 1. 总览（Overview）

Project-X 是由学校运营的考试平台，涵盖答题卡设计、扫描导入、原生 OCR、客观题与主观题判分、多评与仲裁、成绩发布、分析、账号管理、导出及可选的大语言模型分析。系统由 React Web 客户端、Express 服务端、SQLite 或 MariaDB 存储、Electron 扫描客户端、C++ TWAIN/OCR 可执行程序及 Python 大语言模型辅助服务组成。

生产部署指南通过反向代理或 Cloudflare 隧道对外提供仅监听回环地址的 Node 服务。因此，尽管 `startServer()` 绑定 `127.0.0.1`（`src/apps/answer-card/server/index.ts`），互联网攻击者仍可能访问 Web/API。Electron 扫描端通常运行内嵌本地服务，也可以通过扫描端 API 密钥向学校远程服务器上传数据。

价值最高的资产包括管理员和教师凭据、扫描端 API 密钥、模型服务密钥、学生身份与班级关系、成绩和排名、未发布考试、手写答案图像、原始试卷、批注、审计历史及数据库备份。完整性尤其重要：细微的判分、页面配对、排名、发布或授权错误，即使不像传统攻击，也可能影响学业结果。扫描和阅卷期间的可用性同样具有重要的运行价值。

这是单学校系统，不是面向不互信租户的 SaaS。答题卡和部分教师资源在同一安装实例内有意共享。因此，应关注学生／教师／管理员、考试、班级、学科、题块、发布状态和扫描密钥之间的边界，而不是缺少按客户划分的租户隔离。

## 2. 威胁模型、信任边界与假设

### 参与者与信任边界

- **未认证的网络用户：** 可控制登录请求、请求头、来源、URL 参数、健康检查及意外暴露的路由。公开隧道使新部署接管和拒绝服务成为现实风险。
- **学生：** 拥有合法低权限账号，可能操纵 ID、考试／考试组 ID、查询参数、AI 请求及并发行为。他们只能看到自己的已发布成绩及相关答案裁图。
- **教师：** 属于部分可信的内部人员。学科教师、班主任、年级负责人及旧版“普通教师”具有不同范围；在获授权的范围内控制答题卡定义、导入、试卷、扫描、成绩、批注、公式和 AI 内容。教师账号失陷是主要威胁。
- **管理员：** 按设计控制用户、权限矩阵、备份恢复、模型提供商、数据库配置和全局设置。管理员失陷基本等于整个实例失陷，但破坏性操作仍应可审计，并具备防误操作能力。
- **扫描端／API 密钥客户端：** `scanner`／`full` 密钥是机器凭据，不是用户身份。它们能够同步广泛的考试／答题卡数据并提交扫描，应将持有者视为具有较强权限的服务角色。
- **不可信文件与内容：** 恶意授权用户或被攻陷扫描端提交的答题卡 JSON、CSV/XLSX、图像、PDF、DOCX、ZIP 备份、文件名、OCR 结果、手写内容、批注和模型输出均可由攻击者控制。
- **外部服务：** 配置的模型端点接收试卷内容或匿名化的成绩汇总，返回不可信模型输出。DNS、服务可用性、计费、保留策略及提示行为不受 Project-X 控制。
- **运维人员控制的输入：** 环境变量、隧道／代理配置、`config.yml`、数据库凭据、`PROJECTX_AUTH_ENFORCE`、CORS 来源、数据路径、识别器路径、保留设置及模型辅助服务配置。这些配置只在对抗远程攻击者时视为可信，不能用于防御恶意主机管理员。
- **开发者控制的输入：** 迁移、schema、构建／打包脚本、原生二进制、依赖、测试夹具和演示数据工具。利用通常需要先攻陷仓库或构建链，运行时审查优先级较低。

### 安全假设

生产环境必须启用认证、在代理处使用 HTTPS、通过专用操作系统账号运行、保护数据目录，并在分发访问 URL 之前修改初始化凭据。MariaDB 和模型辅助服务不应独立暴露到互联网。假定扫描工作站和 API 密钥分发渠道受到物理管理。

认证使用随机、不透明的 Bearer 令牌，首选放入 `HttpOnly`、`SameSite=Lax` Cookie；跨源模式仅在内存中持有令牌。令牌在磁盘上以 SHA-256 哈希保存，8 小时或 30 天后过期。没有多因素认证；密码最低要求仅六个字符；令牌不绑定设备。

固定初始化管理员密码 `admin123` 会写入 `bootstrap-admin.txt`，并要求首次改密（`src/server/db/index.ts`）。新建或恢复的部署若已对外暴露，攻击者可使用文档中的密码登录并立即完成改密流程。即使有强制改密和登录限流，这仍是严重的部署竞态。

RBAC 在服务端执行且默认启用。不过，为兼容旧行为，没有细粒度角色或权限记录的教师会有意获得较广访问权限，小测模式考试也对所有教师可见（`server/middleware.ts`）。若符合学校政策，这些不是漏洞；若运维人员误以为系统默认拒绝并严格隔离，则可能产生严重后果。

## 3. 攻击面、防护措施与攻击场景

### 认证、会话与授权

`routes/auth.ts`、`AuthService.ts` 和 `middleware/auth.ts` 实现了 bcrypt 哈希、通用登录错误、IP／账号登录限制、HttpOnly Cookie、改密后会话撤销、强制替换初始密码及非活跃账号检查。API 密钥随机生成，以哈希保存，具有权限范围、可撤销，且只在创建时返回明文。

每条路由都应同时检查功能权限和对象范围。`requireExamAccess`、教师可见性、发布门禁和题块级 `requireGradingScope` 是重要控制。只按裁图／批注／分配 ID 寻址的路由可能成为绕过入口。例如，`review-annotations.ts` 检查通用阅卷权限，却不确认裁图所属考试／题块范围或批注归属；阅卷裁图列表也只检查考试访问，没有题块范围。教师可能枚举裁图 ID、读取其他题块、对未授权答卷创建批注，或删除其他阅卷者的批注。仲裁还有指定仲裁员和考试检查，但所有替代路由必须保持一致。

攻击场景包括：学生修改 ID 读取同学尚未发布的成绩；学科教师通过考试组、导出、裁图、仪表板或扫描路由访问其他班级；教师修改分配题块之外的成绩；持扫描密钥提交伪造识别数据。UI 身份／角色覆盖只能用于展示，不能影响授权。

### 判分与业务语义完整性

核心风险集中在 `shared/grading.ts`、成绩编辑、扫描持久化、阅卷服务、仲裁、排名更新及考试发布。需测试重复学号、单双面页面分组、重试、部分上传、扫描后编辑答题卡、修改答案、小数／半分规则、总分与逐题模式、缺少考生、多评异常值、并发领取、仲裁资格、赋分公式、并列排名及 SQLite/MariaDB 等价性。

现有健壮性措施包括分数／满分校验、权威题目覆盖检查、事务、upsert、乐观并发／CAS 仲裁更新、领取归属、重新分配限制、自动重算排名、缓存失效及成绩变更时自动撤回发布。仍需寻找文件与数据库部分提交、陈旧卡片布局、重试将裁图附到错误考试，以及 SQLite 异步事务包装中的竞态。悄然将某个学生的页面或分数分配给另一学生的逻辑错误，可能比有限的信息泄露更严重。

### 上传、解析器、原生进程与可用性

图像、试卷、识别、扫描和恢复端点通过 Sharp、PDF.js、Mammoth、Tesseract、AdmZip、OpenCV、PDFKit 和原生程序处理复杂的攻击者可控格式。图像路由通常结合扩展名／MIME 检查、魔数验证、安全文件名、生成式文件名及大小限制。原生命令使用参数数组而非 Shell，并设置识别超时。

覆盖并不均匀：试卷验证主要相信扩展名；识别上传的 Multer 声明中没有同等文件过滤；解析器级解压和像素限制需要检查。单文件限制不等于整个请求限制：40 份各 50 MB 的试卷或 50 个保存在内存中的裁图上传可能耗尽 CPU、内存或磁盘。除登录外，没有通用 API 或 AI 限流。进入 C++/OpenCV 的畸形图像可能将解析器缺陷转化为服务器或扫描端远程代码执行。ZIP 恢复有目录穿越检查且仅管理员可用，但解压总量、条目数量及 ZIP 炸弹仍需关注。

### AI 与隐私

模型提供商密钥以 AES-256-GCM 加密，API 密钥和会话则以哈希保存。Python 辅助服务要求内部 Bearer 密钥，不提供原始 SQL 工具，将工具调用限制在选定考试／考试组／班级，并验证提供商 URL 以降低 SSRF 风险。支持公网 HTTPS 模型服务及回环 HTTP 推理服务。

自定义提供商 URL 仍涉及出站访问和 DNS 重绑定，应实施网络层控制。上传试卷和提示可能携带提示注入。模型输出必须只用于展示，不能授予操作权限或直接修改成绩。需确认学生 AI 请求始终限制为学生自身：`callerRole`、`studentId` 等字段不在 Python 请求 schema 中，而工具会返回班级／考试汇总。也应评估小班级的重新识别风险，以及运维人员是否明确同意向第三方发送原始试卷或教育记录。

### 浏览器、Electron、存储与运行维护

React 转义及未启用原始 HTML 的 ReactMarkdown 可降低 XSS 风险。安全响应头、`nosniff`、抑制 Referrer、Electron 窗口精确来源检查、上下文隔离、禁用 Node 集成和沙箱都是积极控制。不过 CSP 仍允许内联脚本／样式和广泛的 HTTP(S) 连接，降低了注入后的防护价值。扫描 API 密钥在 localStorage 中保存 30 天，因此扫描端来源的 XSS 或本地浏览器配置盗取可导致泄密。媒体／SSE 的跨源 Bearer 令牌可能出现在查询字符串，带来代理日志和浏览历史泄露风险。

CORS 使用允许列表，Cookie 为 SameSite=Lax，不允许的来源不能读取响应，但没有显式 CSRF 令牌。如果受信来源、同站子域或 Cookie 策略变化，应重新评估。应在所有渲染器中测试上传名称／批注的存储型 XSS，并测试表格导出的公式注入。

备份含数据库、图像、凭据／初始密码。字段加密能保护“只复制数据库、未获得密钥”的情形，不能防御主机失陷；根据 `ANSWER_CARD_DATA_DIR` 设置，`secret.key` 可能随数据进入备份。为支持管理员导出，初始密码仍以可逆加密保存。需限制备份访问和保留期、文件系统 ACL、日志及服务账号主目录文件。构建脚本和仓库中的原生二进制属于供应链攻击面，但若没有更新／构建链失陷，无法通过远程直接利用。

## 4. 严重程度校准

### 严重（Critical）

- 未认证或学生级身份接管管理员，包括在公开部署中抢先使用 `admin/admin123` 完成初始化，取得全部记录和成绩控制权。
- 可达上传导致 Node／Python／原生解析进程远程代码执行，或获取完整数据库及可用的解密材料、会话或 API 密钥材料。
- 对大量考试／学生成绩进行隐蔽、可规模化的破坏或重新归属，尤其当结果已作为权威成绩发布。

### 高危（High）

- 教师或扫描密钥越过班级／学科／考试／题块边界，读取大量可识别学生身份的试卷或修改成绩。
- 绕过发布控制，向学生披露广泛的未发布成绩或答案。
- 已认证低权限请求在学校运行期间持续耗尽内存、磁盘、原生进程或 AI 费用。
- SSRF 到达敏感内部服务或云元数据；按配置调用公网模型服务本身属于预期行为。

### 中危（Medium）

- IDOR 泄露一个考试／班级、答案裁图、批注集合或有限学生记录，未修改成绩。
- 需要教师查看攻击内容的存储型 XSS；在现实 Cookie／来源条件下造成实质状态变化的 CSRF；导出文件中的公式注入。
- 可恢复的排名、舍入、阅卷分配或单个学生成绩错误，具有审计证据且可由管理员纠正。

### 低危（Low）

- 版本／路径／时间元数据泄露、有界的未认证健康探测、轻微日志泄露或退出登录 CSRF。
- 需要已具备权限的工作站用户才能利用的本地问题，或仅在运维人员主动禁用认证后才出现的不安全行为。
- 单学校部署不纳入跨租户隔离问题；开发脚本和夹具风险较低，除非进入生产或构建链。
