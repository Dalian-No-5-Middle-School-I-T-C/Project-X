## 概要

此问题由本次修改引入。在该修改范围之前，只要阅卷人 ID 已出现在 score_breakdown 中，其再次提交就会被无条件拒绝，提交次数也被限制为 reviewMode。本次提交把这两项控制改为仅在答题图不处于 disputed 状态时生效，并增加两个评阅轮次，却没有要求由不同阅卷人提交，也没有验证请求者是否为自动指派的争议评阅人。

修改后的重复评阅检查，只会在答题图不是 disputed 状态时拒绝已有阅卷人。两次评阅出现分歧后，任何先前参与的阅卷人都可以再次 POST 同一答题图；新增的 reviewMode + 2 上限会接受这一重复轮次，而不核实请求者是否为新指派阅卷人或指定仲裁人。随后，computeMultiReviewResult 会把重复分数当成独立观察值。例如，当阈值小于 10 时，[10, 0] 会形成争议；原先提交 0 分的阅卷人再次提交 0，结果变成 [10, 0, 0]。中位数聚类算法将两个 0 视为多数，把 10 作为离群值排除，将 0 写入 question_scores，并重算学生总分。这还会绕过已配置的仲裁人，因为系统只禁止仲裁人通过初评路径提交，却仍允许先前阅卷人继续提交。利用需要拥有 grade:write、能够访问目标考试的教师账号，以及已经存在争议的多评答题图。操纵行为可从评阅历史中看到，每次请求只影响一张答题图，但可以对多份争议试卷重复执行，直接损害独立评阅的完整性。

## 证据注释

1. 可通过网络访问的提交端点要求普通成绩写入权限，但不区分自动指派的争议阅卷人与先前阅卷人。
2. 3P+ 解析器把同一阅卷人的两次相同提交当成邻近中位数的多数，使 [10, 0, 0] 可以得出 0 分，并排除另一人的独立评分。
3. 修改后的检查明确允许已有阅卷人在 disputed 状态下再次提交，并允许最多 reviewMode + 2 个轮次，却不检查请求者是否为新指派阅卷人。
4. 重复提交作为一次完整评阅追加到历史中，参与多数计算；一旦被认定为争议已解决，结果就会写入题目成绩和学生总分。

## 攻击路径分析

技术校准结果为中等影响乘以低发生可能性，按矩阵对应低严重性。只要前提成立，完整性影响确实存在，可执行验证也证明了这种条件性行为。不过，最终策略仍排除此问题：概念验证通过受保护的数据库写入预置了争议记录，而当前数据库结构下，正常创建答题图时 review_round 默认为 1，ReviewService 却按其从 0 开始的方式限制轮次。这似乎阻止普通教师在该提交版本中产生所需的多评争议状态，且未找到其他生产写入路径。因此，仓库证据未能证明低权限攻击者可以现实地达成前提。排除原因是该前提受保护或极不现实，而不是服务绑定回环地址或要求认证。

### 路径

先前参与评阅的已认证教师 → 发送已认证远程请求 → 文档记载的公共 Cloudflare 隧道连接回环 Node 服务 → 将 HTTPS 流量转发至 127.0.0.1:5174 → POST /api/review/exams/:examId/block-crops/:cropId/submit → 要求考试访问权和评阅权限 → 检查 grade:read、grade:write 及考试可见性 → 后续没有指派或预期阅卷人授权检查 → disputed 状态禁用重复评阅检查 → 允许已有阅卷人再次提交 → 重复分数追加至 score_breakdown → 全部条目被计为独立观察值 → 3P+ 邻近中位数多数解析器计算结果 → 写入解决后的成绩，并重算总分和排名 → 影响 question_scores、student_scores 和排名。

攻击情景：一名此前已对争议答题图给出评分的教师，通过普通评阅 API 再次提交其希望采用的分数。路由虽然认证教师、检查成绩权限及考试可见性，但服务在状态为 disputed 时明确关闭重复评阅检查。它随后追加重复分数，将所有历史条目传入不区分独立阅卷人的解析器。因此，同一教师的两个相同条目可能成为邻近中位数的多数，进而覆盖学生的权威成绩。提供的可执行验证通过已认证 Express 端点确认了这一条件性影响，包括 question_scores 和 student_scores 的变化。操作仍记录在 score_breakdown 中，每次请求仅限一张答题图，因此影响为中，而非高。决定可报告性的限制在于：在该确切提交版本中，前提是否可达。仓库默认把 review_round 初始化为 1，服务却按从 0 开始的方式递增并限制轮次。这似乎阻止了创建正常争议答题图所需的第二次评阅，而且没有找到其他生产代码会写入 disputed 状态。因此，验证必须预置数据库记录。存在问题的分支仍应修复，但缺少现实可行的低权限前提达成路径，触发了最终策略排除。

## 发生可能性

低（Low）。如果已经存在符合条件的争议记录，利用很简单，提供的可执行概念验证也通过正常认证 HTTP 端点确认了这一点。公共隧道部署可使端点远程可达，普通教师也拥有所需的成绩权限。然而，当前数据库结构把 review_round 初始化为 1，服务却将其视为从 0 开始，这似乎会拒绝原本应产生争议状态的那次评阅。没有找到其他生产代码会写入 disputed 状态。已恢复或手工修改的数据库仍可能包含这类记录，但仓库证据未能证明这构成现实的低权限攻击路径。

## 影响程度

中（Medium）。成功请求会修改其他学生的权威单题成绩、总分，并可能改变排名，越过独立评阅和仲裁的完整性边界。影响被限制在有效分数范围内，每次请求只涉及一张答题图，需要教师账号，且可从评阅历史中发现。所提供的威胁模型将有审计证据、可恢复的单个学生成绩修改归为中等影响。

## 控制措施

- 认证默认启用，接受不透明 Bearer 令牌或认证 Cookie。
- /api/review 挂载点检查 grade:read，提交路由另行要求 grade:write。
- requireExamAccess 将有范围限制的教师限制在可见考试内，并阻止学生访问该路由。
- 答题图查询要求 crop ID 属于所提供的考试。
- 提交分数会被限制在 0 到所配置题目满分之间。
- 答题图未处于 disputed 状态时，已有阅卷人的重复提交会被拒绝。
- 已配置的仲裁人不得通过初评提交路径参与评阅。
- 争议重评最多允许 reviewMode 加 2 条历史记录。
- 事务更新及 review_round 的比较并交换机制，防止并发覆盖。
- 评阅历史保存阅卷人 ID、分数和时间戳，因此操纵行为可以审计。
- 专用仲裁端点要求请求者为所配置的仲裁人。
- 未发现针对重复成绩提交的一般请求限流。
- 受影响的争议答题图提交没有指派或预期阅卷人授权保护。

## 盲点

- 静态仓库分析无法确定已部署或已恢复的生产数据库，是否已经包含旧版本、人工修正或外部工具创建的争议记录。
- 提供的可执行概念验证证明了存在问题的分支，但它预置了已处于争议状态的数据库记录，而没有通过连续生产 HTTP 请求生成该状态。
- 没有检查实际部署状态，因此文档中的 Cloudflare 入口只证明支持公共暴露，并不证明所有实例都可以公开访问。
- 仓库搜索未发现其他生产代码会写入 disputed 状态，但仓库外的数据库管理或导入流程可能创建该前提。
- 没有动态重建历史数据库与早期应用版本之间的交互。

  // 方法：逐对检查差值的聚类
  // 选取中位数附近的分数群来判断
  const median = sorted[Math.floor(sorted.length / 2)];
  const closeGroup: number[] = [];

  for (const s of sorted) {
    // 从最小分和最大分往中间看，找出差异在阈值内的组
    let isCloseToAny = false;
    for (const c of closeGroup) {
      if (Math.abs(s - c) <= disputeThreshold) {
        isCloseToAny = true;
        break;
      }
    }
    if (isCloseToAny) {
      closeGroup.push(s);
    }
  }
  // 如果 closeGroup 未形成（可能只有一两个），尝试另一种方式
  const closeToMedian: number[] = [];
  for (const s of sorted) {
    if (Math.abs(s - median) <= disputeThreshold) {
      closeToMedian.push(s);
    }
  }

  // 如果 closeToMedian 覆盖了大部分（≥2 个且大于等于一半），且不是全部
  if (closeToMedian.length >= 2 && closeToMedian.length < sorted.length) {
    const avg = closeToMedian.reduce((a, b) => a + b, 0) / closeToMedian.length;
    const outliers = sorted.filter(s => !closeToMedian.includes(s));
    return {
      disputed: false,
      needsArbitration: false,
