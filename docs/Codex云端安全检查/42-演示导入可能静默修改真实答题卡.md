## 概要

此问题由本次修改引入。在基线版本中，如果固定的演示答题卡 ID 已被占用，普通 INSERT 会触发唯一性约束错误，从而阻止导入程序修改该答题卡。新加入的 INSERT OR IGNORE 会忽略冲突，使后续所有种子数据操作都把已有答题卡当作演示答题卡。导入程序应检查插入结果；只有确认已有记录的 is_demo = 1，并且身份符合预期的演示数据时，才能复用该记录，否则应中止操作或分配不会冲突的答题卡 ID。

演示导入使用 88000001、88000002 等固定答题卡 ID。本次提交把答题卡创建语句从 INSERT 改成 INSERT OR IGNORE，却没有核实被忽略的已有记录是否确实属于演示数据。如果生产答题卡已经使用这些 ID，seedExam 会继续将真实答题卡用作演示考试的答题卡。对于存在题目数据的答题卡，ensureDemoObjectiveBlock 随后会向已有答题卡插入演示客观题块及硬编码答案。对于 88000001，seedFillBlankDemo 还会插入演示主观题块、题目和图片资源。seedFillBlankDemo 中过时的注释仍声称，演示 ID 被占用会导致 seedExam 失败，但 INSERT OR IGNORE 已经抑制了这类失败。清理操作只删除 is_demo = 1 的 answer_cards，因此发生冲突的真实答题卡及注入的题块可能在演示数据清理后继续保留。这可能静默改变真实考试及后续判分所使用的布局或答案元数据。操作需要具备 SYSTEM_MANAGE 的管理员主动执行，因此主要属于数据完整性和管理操作安全性缺陷，而非权限边界漏洞。

## 验证

1. 固定演示答题卡 ID 可能与非演示 answer_cards 记录冲突，而 INSERT OR IGNORE 会忽略冲突，不会拒绝执行。
2. 演示导入仍可从生产管理界面触达，要求 USER_MANAGE 和 SYSTEM_MANAGE 权限，并会在插入被忽略后继续执行。
3. 后续生产种子数据逻辑会把演示考试关联到冲突的真实答题卡，并插入归属于该卡的题块、题目、答案、图片元数据和资源文件。
4. 演示数据清理不会删除冲突的非演示答题卡，也不会删除注入的子记录和资源，因此完整性影响会持续存在。
5. 专项测试使用实际服务和数据库结构，复现了 ID 冲突、数据修改、清理后的残留，以及这些修改通过生产仓储查询可见的行为。

## 证据注释

1. 新增的 OR IGNORE 会忽略与已有真实答题卡的冲突，却没有检查记录归属。
2. 插入被忽略后，种子数据逻辑仍继续执行，将演示考试关联到冲突答题卡，并可能向其添加客观题块和答案。
3. 填空题种子数据逻辑直接信任答题卡 ID 88000001，并向其中插入演示题块；其注释错误地假定 ID 冲突仍会在前面引发失败。

## 攻击路径分析

在应用策略排除规则之前，经校准的中等数据完整性影响与低发生可能性，按矩阵对应低严重性。最终策略阶段适用“仅特权用户可执行／受保护写入路径”排除规则：执行需要同时具有 USER_MANAGE 和 SYSTEM_MANAGE 的已认证账号，目前只有拥有通配权限的管理员满足条件，且没有证明存在额外的提权收益。该操作还需要从开发者模式的管理流程中明确发起，并依赖不常见的 SQLite 答题卡 ID 冲突。可执行概念验证证明了缺陷及其持续影响，因此不是误报；但它证明的是管理员引发的数据完整性或正确性故障，而不是现实可行的未授权攻击路径。按所要求的策略，最终可报告性结论因此为忽略。

### 路径

拥有 user:manage、system:manage 和通配权限的已认证管理员 → 明确执行开发者模式中的特权操作 → 向 Express 答题卡服务发送 POST /api/db/import-demo → 路由在 SQLite 上调用 seedDemoData → seedDemoData 使用 INSERT OR IGNORE 插入固定答题卡 ID → 未检查插入结果及 is_demo 所标识的归属 → 继续写入演示考试关联，以及子题块、答案、题目、图片和资源 → 清理时只删除 is_demo=1 的 answer_cards → clearDemoData 保留非演示父记录及注入的子记录 → 常规仓储查询加载残留子记录 → CardRepository 和成绩编辑流程使用被修改的答题卡定义。

攻击情景：恶意或已被攻陷的最高权限管理员，或者误信“演示导入不会影响真实数据”的管理员，在存在固定演示 ID 冲突的 SQLite 实例上调用 POST /api/db/import-demo。导入程序忽略主键冲突，把保留下来的真实答题卡视为演示答题卡，并在其下写入演示子记录。提供的可执行集成测试复现了在 88000002 下写入客观题答案、在 88000001 下写入主观题和资源文件的行为；执行 clearDemoData 后，这些记录仍然存在，并能被 CardRepository 返回。这证明了真实的数据完整性缺陷。然而，低权限攻击者无法执行存在问题的导入操作：路由要求认证、USER_MANAGE 和 SYSTEM_MANAGE，目前只有通配权限管理员满足。教师虽然可能通过可写答题卡 API 准备一个指定固定 ID 的答题卡，但教师本来就拥有广泛的共享答题卡写入能力，而且仍需另一名管理员执行导入。标准创建和导入流程生成新的八位 ID，不保留用户选择的导入 ID，因此偶然冲突并不常见。界面也把此操作放在开发者模式下，并要求确认。因此，该问题属于管理操作完整性缺陷，但按最终策略，不构成可报告的提权或未授权攻击路径。

## 发生可能性

低（Low）。端点可能通过部署代理从远程访问，但利用仍要求采用 SQLite、发生精确的固定 ID 冲突，并由另一名已认证的最高权限管理员主动执行开发者模式操作。普通创建和导入流程生成新 ID，偶然冲突较少。教师可能通过可写答题卡 API 植入指定 ID，但其本来就拥有广泛的共享答题卡写入权限，且无法在没有管理员配合时触发导入。因此，发生可能性为低。

## 影响程度

中（Medium）。已证明的影响是持续修改一个或多个发生冲突的答题卡定义，包括硬编码答案、主观题、图片元数据和资源。这些定义会被正常产品流程及成绩编辑路径读取，可能改变使用该答题卡的考试布局或判分元数据。动态验证没有直接证明学生成绩发生变化；影响范围也仅限于少见的冲突答题卡，管理员能够定位并修复记录，因此影响为中，而非高。

## 假设条件

- 受影响部署使用 SQLite；该路由明确拒绝 MariaDB 部署。
- 某张 is_demo=0 的合法答题卡已经使用固定演示 ID，尤其是 88000001 或 88000002。
- 同时拥有 user:manage 和 system:manage 的已认证管理员主动执行演示数据导入。
- 冲突答题卡仍与真实考试关联，或仍被正常答题卡、判分、成绩编辑流程使用。
- 远程可达性取决于部署方式：仓库中的服务绑定到 127.0.0.1:5174，而所提供的威胁模型说明，生产环境通常通过反向代理或 Cloudflare 隧道对外提供访问。

原文另列前提：

- 部署使用 SQLite。
- 已存在非演示答题卡，其 ID 与 88000001、88000002 等固定演示 ID 完全相同。
- 已认证用户同时拥有 USER_MANAGE 和 SYSTEM_MANAGE；仓库注释说明，目前只有通配权限管理员满足条件。
- 该特权用户调用 POST /api/db/import-demo。
- 冲突答题卡随后被真实考试流程读取或使用。

## 控制措施

- 启用认证强制执行时，authMiddleware 要求有效会话。
- /api/db 路由组要求 USER_MANAGE。
- POST /api/db/import-demo 额外要求 SYSTEM_MANAGE。
- 当前默认权限映射只向通配权限管理员角色授予所需权限。
- 强制修改密码中间件先于受影响业务路由执行。
- 路由拒绝 MariaDB，只能在 SQLite 部署上执行。
- 界面将演示导入放在开发者模式中，并显示确认提示。
- 服务直接绑定回环地址，但部署反向代理可能使其能够从远程访问。
- answer_cards.id 是主键，但 INSERT OR IGNORE 抵消了原本会阻止导入的冲突错误。
- 清理逻辑保护 is_demo=0 的父记录免于删除，但无法阻止或清除注入的子记录。

## 盲点

- 提供的概念验证直接调用 seedDemoData，没有重放 HTTP 请求；不过 HTTP 路由只是一个很薄的认证封装，其可达性和权限要求在源码中明确可见。
- 验证证明了持续的数据修改以及仓储读取行为，但没有完整执行一次改变已发布学生成绩的判分流程。
- 所审查工作区中的部署清单没有确定某个具体的公共反向代理、主机名或负载均衡器；远程暴露依据来自所提供的生产威胁模型。
- 仓库证据不能说明真实实例在创建生产答题卡后导入演示数据的频率，也不能说明生成的 ID 与固定演示范围冲突的频率。
- 拥有 GRADE_WRITE 的教师似乎可以向固定答题卡 ID 发送构造的 PUT 请求，但分析没有动态执行这条准备路径。由于答题卡按设计共享，且教师具有广泛写入权限，这也不会带来有意义的权限提升。

function seedFillBlankDemo(db: Database.Database): void {
  // 卡片不存在时跳过（防御性检查；演示卡号被真实数据占用时 seedExam 的 INSERT 会先行报错）
  const card = db.prepare("SELECT id FROM answer_cards WHERE id = ?").get(FILL_BLANK_CARD_ID) as { id: string } | undefined;
  if (!card) return;

  const blockId = "fb-demo-1";
  db.prepare(`
    INSERT OR IGNORE INTO subjective_blocks (id, card_id, sort_order, block_kind, title)
    VALUES (?, ?, 0, 'fill_blank', '填空题（演示）')
  `).run(blockId, FILL_BLANK_CARD_ID);
