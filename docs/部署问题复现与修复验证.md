# 部署问题复现与修复验证

验证日期：2026-09-21。范围为本地隔离环境，未发布、未迁移生产数据。

## 验证环境与方法

- 服务端：WSL Ubuntu 24.04、Node.js 22.16.0、真实 MariaDB 10.11.14；关闭 Linux 本机扫描能力，启用远程扫描端上传 API。Web 地址为 `http://localhost:15174`。
- 扫描端：Windows 本地 API、实际 C++ OMR 识别器及扫描端 Web 构建，地址为 `http://127.0.0.1:15175`。通过 Browser 插件操作页面、原生文件选择器和目录选择器；没有用浏览器脚本绕过页面调用业务 API。
- 使用隔离测试数据库、测试学生、合成填涂图片和本地测试 Key。图片中学号和选择题填涂由真实 OMR 识别；服务端保存成绩和扫描回执后另行查询数据库核对。
- AI 使用本地请求验证桩，检查 DOCX 提取文字和请求模式，返回固定知识点。验证了前端至分析请求的链路，**没有验证真实模型回答质量或实际 Python AI 服务启动**。
- 未进行 Electron 安装包安装验收，也没有连接用户的 KODAK 实体扫描仪。

## 1. DOCX 原卷分析

**复现：** 上传 DOCX 后，在 PDF 导出检查中点击分析，返回“未找到原卷文件”。另外，题目范围初始值为中文“全部”，判断逻辑却使用 `all`，使默认单选项未选中。

**原因与修复：** 多模态模型走直接文件输入，而文件收集器只接受 PDF/图片。纯 DOCX 原卷现在提取文字并按文本请求发送，即使所选模型支持视觉也不会把 DOCX 当作图片。支持按数字页序提取多个 DOCX；空文档不会被送给图片 OCR，也不会静默略过而只分析剩余文档。默认题目范围统一为 `all`。

**结果：** 在原 PDF 检查流程直接点击“开始分析”，显示“已分析 1 道题”，可以进入导出。自动回归覆盖多 DOCX 页序、空文档、缺失文件、图片仍按直接输入处理，以及返回知识点。

限制：DOCX 中只有嵌入图片、无法提取文字的原卷仍会提示提取失败；本次不新增 Word 渲染/OCR 功能。

## 2. 应考名单

**复现：** MariaDB 搜索学生报 SQL 错误；第一次打开名单时，人数与缺考计数可能不一致。原“清除显式名单”实际执行恢复预设班级/年级名单，原“保存”完成后重新打开同一窗口，容易被理解为按钮只刷新。

**原因与修复：**

- 搜索 SQL 使用反斜杠作为 `ESCAPE`，在 MariaDB 中产生不完整字符串。改为 `ESCAPE '!'`，并转义 `!`、`%`、`_`；反斜杠按普通字符搜索。
- 先初始化自动名册快照，再读取当前名单，保证首次响应一致。
- 新增“清空待选名单”，只清空当前编辑内容，便于重新添加实际考生。
- 原恢复行为明确命名为“恢复班级/年级名册”；保存成功关闭窗口，失败信息在窗口内显示。
- 不允许把空名单保存为显式应考名单，避免改变既有成绩发布完整性规则；清空后需先添加实际考生。

**页面验证：** 清空预设人员 → 搜索其他班学生 → 添加 → 保存 → 重新打开，显示所选显式名单。恢复按钮显示原班级两名学生；再次清空并添加实际两名考生，保存、重开后仍为两人。

## 3. TWAINDSM.dll

**确认修复的代码问题：** 显式 DLL 路径使用 ANSI 接口读取和加载，不能正确处理部分 Unicode 路径。改为 UTF-16 的 `GetEnvironmentVariableW` / `LoadLibraryW`，加载失败记录 Win32 错误码。

**验证：** ia32、x64 扫描桥都编译成功。使用测试 DSM 数据源验证：DLL 放在包含中文和特殊字符的独立路径，并通过 `TWAIN_DSM_DLL` 指定时，原版不能枚举测试源，修复版可以。

**必须保留的边界：** 将 DLL 正常放在 EXE 同目录的补测中，原版与修复版都可通过 Windows 备用搜索加载。因此不能笼统认定“中文安装目录”就是用户现场故障原因。附件日志记录的是 `Failed to open scanner: KODAK Scanner: i3000`，没有足够信息证明是上述路径问题。实体设备、驱动位数、DLL 依赖和现场安装包仍待验收，不能宣称第 3 项现场故障已经解决。

仓库只保留源代码修改，不提交生成的 EXE。发布扫描端前需按目标架构运行 `scripts/build-scanner-bridge.bat ia32` 或 `scripts/build-scanner-bridge.bat x64`，再打包；仅运行 Web/扫描端 TypeScript 构建不会更新原生桥。

## 4. 扫描上传

发现三个独立问题：

1. 旧“测试连接”只检查健康与上传 API 开关，错误 Key 也能显示服务器可达。新增不创建扫描会话的 `/api/scanner/upload/check`，沿用上传认证；页面同时验证 Key 权限并显示错误。旧服务端不支持此接口时明确提示升级。
2. 创建会话因错误 Key 失败后，上传任务仍持有旧 Key。现在只在“尚未创建远端会话、服务器地址未改变”时，显式重试读取修正后的 Key；已有会话和其他服务器的任务保持原凭据边界。
3. 实际上传还复现了 MariaDB `Illegal mix of collations`：用户学号列与后来创建的扫描回执学号列排序规则不同，提交阶段的列间 JOIN 报错。改为分别绑定同一学号参数，保留原回执、考试、成绩和删除范围约束，无需迁移现有表排序规则。

**页面及数据库验证：**

- “导入图片”使用真实 OMR 识别出测试学号，成绩 50/50；复现提交错误后修复，在页面点击原任务重试，显示“上传完成，1 页已提交到服务器”。
- “导入目录”通过目录选择器读取图片，识别出另一测试学号，成绩 50/50。错误 Key 的连接测试显示“无效的 API Key”，实际上传显示创建会话失败。改正 Key 后，连接测试显示“服务器可达，上传权限有效”，原任务重试可以创建会话并上传。
- 目录提交随后被先前验收设置的测试考试关闭状态拦截。将隔离测试考试恢复为阅卷中后，浏览器页签暂时无法交互，最后一步使用同一任务的实际提交接口完成，返回 HTTP 200、1/1 页完成。此最后一步不记为前端点击验收通过。
- 最终 MariaDB 中两个测试学生各有一条 50 分成绩和一条 `saved` 回执，没有重复成功回执。

## PR #284 自动审核补修

基于 `9331d07` 核实两条 codex-connector 意见，均属实：

- 混合原卷会遗漏部分页：现在 DOCX 与 PDF/图片混合时，在文本、视觉两种分析模式及文本提取入口均返回 `400 MIXED_PAPER_FORMATS`，提示统一格式后重新上传，不把部分内容发给模型。本次选择明确拒绝，而未新增混合文档渲染功能。
- 并发 DOCX 解压缺乏资源边界：改为串行流式校验后调用 Mammoth。每份原卷最多 40 个 DOCX、4096 个 ZIP 条目，累计压缩内容不超过 20 MiB、实际解压内容不超过 32 MiB、提取文字不超过 524288 字符。使用 yauzl 校验真实解压输出，防止伪造 ZIP 大小绕过限制；Mammoth 使用同一份已校验 Buffer。每个服务进程只允许一个 DOCX 提取任务，忙时返回 429，超限返回 413，损坏或不支持的压缩包返回 422。

依赖清单、锁文件和 Ubuntu 服务端运行依赖白名单同步加入 yauzl。

补充回归在 Windows 和 WSL Node.js 22 均通过：纯 DOCX 数字页序、两种模型下三种混合顺序、高压缩率样本、伪造解压大小、多文档压缩/解压/文字累计超限、并发拒绝及失败后恢复。Web、扫描端和服务端完整构建（含类型检查）通过。此补修不涉及 SQL 或数据库结构变更。

### 后续“yauzl 流错误导致提取挂起”意见核实

基于 `9a6b8a3`，未复现该意见描述的挂起。当前生产直接依赖及 Ubuntu 包指定 `yauzl ^3.2.0`，锁定版本为 3.2.0；该版本通过 `_destroy(err, cb)` 调用 `cb(err)` 完成销毁生命周期。Electron 的 extract-zip 间接依赖仍有 yauzl 2.10.0，其实现确实直接覆盖 `destroy()`，但 DOCX 提取不使用这份嵌套依赖。因此，该意见关于流生命周期的前提不适用于当前分析代码。

新增 `node --import tsx scripts/verify-docx-stream-errors.ts`，在独立子进程中设置超时，并构造首次读取超长、中途读取超长、结束时长度不足三种实际 ZIP 校验错误。每个用例均检查返回 `INVALID_DOCX`，并在同一进程继续提取正常 DOCX，确认全局名额已释放。Windows Node.js 25.8.2、WSL Node.js 22.16.0 均全部通过；既有 HTTP 部署回归再次通过。保留测试与核实记录，未因这条未复现意见改写生产流处理代码。
