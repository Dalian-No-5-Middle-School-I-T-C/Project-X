# 发布构建与服务器更新时间

*落笔于 2026-11-03；对应工作流 `.github/workflows/release.yml`。*

## 这套工序解决什么

发布原本全靠手工：改 `package.json` 版本、在本机跑打包、到 Releases 页面手动传包、再回官网改文案。
断点很多，直接后果是 GitHub Releases 停在 `V1.9.6`，而主干已经走到 v2.7.x——教师按 Releases 下载拿到的是旧包。

现在把「出包 + 上新」收到 CI 里：

- 推 `v<版本号>` 标签 → 构建 32 位扫描端安装包与 Ubuntu 服务端包，生成校验和清单，建 GitHub Release 并附上产物。
- `workflow_dispatch`（Actions 页面手动点）→ 同样构建并上传工件，但**不建 Release**，用来验证发布链路本身。
- 版本号仍以 `package.json` 为准，工作流不替你改版本号；标签与 `package.json` 不一致就直接失败。
- 官网文案不在这里自动改：本轮口径是「只更新 GitHub Release，站点由维护者自己更」。

## 怎么发一版

1. 按发版流程更新 `package.json` 的 `version` 与 `readus/CHANGELOG.md`，走 PR 合入 `main`。
2. 在合入后的提交上打标签并推送：

   ```bash
   git tag v2.7.2
   git push origin v2.7.2
   ```

3. 打开 Actions 的 `Release build` 运行，等五条作业（版本闸门、两条扫描端线、服务端包、发布）。
4. Releases 页面出现 `Project-X v2.7.2`，资产包括：
   - `答题卡扫描端-<版本>-ia32.msi`
   - `project-x-server-ubuntu24-<版本>.zip`
   - 每条构建线各自的 `*-SHA256SUMS.txt` 与 `*-BUILD-INTEGRITY.txt`
5. 官网（宣传站 / 五中官网）的版本文案按各自仓库的检查单手工同步。

只想验证链路而不发布：Actions → `Release build` → Run workflow，可勾选只构建扫描端或只构建服务端包。

## 32 位安装包的两条构建线

`resources/native/win-ia32/` 里随包的识别器与扫描桥由 `native-ia32.yml` 的 `[build-native]` 工序产出，
并由 `verify:scanner-page-timeout` 的 ⑥ 长期核对「包内件含源码现有的关键行为」。发布构建**只复用入库件**，
不在这里重编 OpenCV/识别器（重编约 7 分钟且产物不逐字节可复现，仍走那条工序）。因此两条线都从
`resources/native/win-ia32/` 预置 stage 目录，再执行同一条 `node scripts/package-scanner-win32.cjs --skip-native-build`。

预置口径与 `build-native-mingw.sh` 的产物同构：三件可执行 + `source-sha256.txt` + `licenses/`，其中 TWAIN
第三方声明从 `native/ScannerBridge/third_party/THIRD_PARTY_NOTICES.md` 补进来（随包的 `licenses/` 里本来没有
这一份，缺它等于把声明漏掉）。另外带上 `ucrtbase.dll` 与 15 颗 `api-ms-win-crt-*.dll`。

这里要把两种「静态链接」分清：交叉构建确实把 OpenCV 与 libstdc++ 静态编进了可执行文件，但 C 运行库不是——
识别器的导入表用的是 `api-ms-win-crt-*` 那一组。UCRT 按 app-local 随包正是仓库留着这批 DLL 的原因：缺运行库的
老 32 位工作站会以 `0xC0000142` 退出（同一说明见 `scripts/stage-vc-runtime.cjs` 与 `recognition.ts`）。
真正不带的是 `msvcp140*` / `vcruntime140*` / `concrt140.dll` / `opencv_world4130.dll`：那批属 MSVC 工序
（`npm run native:build:ia32`）的布局，交叉件的导入表里没有它们，带上只会让安装包白胖约 90 MB。

打包之前两条线都先跑 `npm run verify:scanner-page-timeout`，其中 ⑥ 会核对入库的两颗 ia32 exe 确实含源码现有的
关键行为。不跑这一步就等于 CI 闭眼把仓库里现成的二进制发出去。

两条线的差别只在「谁来编 MSI」：

| 线 | 构建机 | 说明 |
| --- | --- | --- |
| `scanner-ia32-windows` | `windows-latest` | WiX 原生运行，不需要 Wine；与现场「macOS/Linux 准备 + Windows 编 MSI」的工序同形 |
| `scanner-ia32-linux-wine` | `ubuntu-latest` + Wine | 不装 MSVC 也能出包，代价是 WiX 要在 Wine 下跑，历史上这一步最容易不稳 |

两条同时跑是为了实测哪条在 CI 上真的绿；结论确定后保留可用的一条，另一条删掉，不留「常红的参考」。
实测结论记在本文件末尾。

### 打包脚本为此做的三处改动

- `run()` 在 Windows 上把 `npm` 解析成 `npm.cmd`：`execFileSync` 不走 shell，直接传 `"npm"` 会 `ENOENT`。
- 新增 `--skip-native-build`：只跳过 MinGW 原生编译，其余工序（前端与服务端构建、依赖装配、PE 架构核对、
  MSI 打包、包内件复核、校验清单）一步不少。它与 `--prepared` / `--verify-msi` 互斥，同时给出直接报用法错误。
  缺件时**在装依赖之前**就报错，不会跑到最后一步才发现 stage 目录是空的。
- 包内入口文件的核对改成按本机分隔符拼路径。原来写死 `"dist/scanner/index.html"` 这类正斜杠字面量，
  而 `@electron/asar` 是按 `path.sep` 切分归档路径的——在 Windows 构建机上永远查不到，会在 MSI 已经编好之后
  误报「缺入口文件」，把整条线判红。实测过：同一份归档，正斜杠查不到、`path.join` 查得到。

`npm run package:scanner:win32:cross` 的行为没有改变：不带新开关时仍按原样先编原生件。

## 服务器更新时间

构建服务端产物时，`npm run build:server` 会在 `dist/server/` 下多写一份 `build-info.json`：

| 字段 | 含义 | 取不到时 |
| --- | --- | --- |
| `version` | `package.json` 的版本号 | `null` |
| `commit` / `commitShort` | 构建所在提交 | `null` |
| `commitDirty` | 构建时工作区是否有未提交改动 | `null`（未记录，不等于干净） |
| `builtAt` | 构建时刻（ISO-8601 UTC） | 缺它整份信息判为不可用 |
| `ciRef` / `ciRunUrl` | CI 的分支或标签、那次运行链接 | 本地构建为 `null` |

服务端启动后从与服务端产物同目录读它（`PROJECTX_BUILD_INFO_PATH` 可指向别处，用于自定义部署布局）。
Ubuntu 包和解包后的 `/opt/project-x-server/dist/server/build-info.json` 随包一起走，不需要额外配置。

管理员在「控制台」页面的**服务器版本与更新时间**区块看到：版本、构建时间、构建提交、本次启动、已运行、
运行环境（Node 与平台）。两个时间各有各的用处：

- 构建时间已更新、本次启动更早 → 新包到位但服务没重启。
- 两者都很旧 → 这台服务器跑的还是旧包。
- 显示「—」→ 这次运行没有可用的构建信息（源码直跑、旧版部署包，或 `build-info.json` 缺损），
  接口同时给出原因文案。**不会**拿当前时间冒充构建时间。

接口是 `GET /api/admin/console/build`，与其他控制台端点同样要求 `system:manage`；响应只给文件名，
不给目录，`Cache-Control: no-store`。公开的健康检查 `/api/app/health` 没有加任何新字段。
「本次启动」在模块加载时定一次，是固定事实：每次请求用 `now - floor(uptime)` 反推的话，取整跨秒会让这一格
抖动一秒，管理员刷新页面会以为服务在反复重启。

构建信息只认与服务端产物同目录的那一份（`PROJECTX_BUILD_INFO_PATH` 可显式指定，用于自定义布局）。
**不按 cwd 兜底**：源码直跑时仓库里那份 `dist/server/build-info.json` 属于上一次构建，把它当成本次运行的
构建时间，恰好会误导「这台服务器是不是新包」这个判断——源码直跑就该显示「—」。

回归：`npm run verify:build-info`（临时 SQLite 库 + 临时 HTTP 服务，已接入 CI）。

## 已知边界

- **两条 MSI 线并存期间不要用标签发正式版本**。两条线都写 `release/答题卡扫描端-<版本>-ia32.msi`，
  同名不同物（构建机不同）。发布作业遇到同名不同物的资产会直接失败，而不是随便挑一个发出去；
  等实测结论定了、删掉一条线，标签发版才可用。这期间用 `workflow_dispatch` 出工件做验证。
- 重跑同一个标签会被拒（`gh release create` 不会覆盖已有 Release）：要重发就先删那条 Release，或按发版流程升版本号打新标签。
- **服务端包必须在 LF 检出上打**。`package-server-ubuntu.cjs` 会核对随包 Linux 补识别器的源码摘要，
  而 `core.autocrlf=true` 的 Windows 工作副本会把 `native/**` 检出成 CRLF，字节摘要自然对不上。
  旧代码在此处只会抛「源码变了，请重编」，把人往错误方向引；现在会区分两种成因，CRLF 时直说是检出问题、
  要换到 LF 检出（Linux 构建机或 CI），源码真变了才维持原来的拒绝。CI 的 ubuntu runner 是 LF 检出，不受影响。
- 原生件不逐字节可复现：同一份源码两次构建出的 exe 大小与关键字符串相同，SHA256 不同（PE 头有构建时间戳）。
  核对请看包内字符串与实际运行，不要只比哈希。
- 安装包仍未代码签名（仓库不含证书），首次安装会有 SmartScreen「未知发布者」提示；发布说明与
  `BUILD-INTEGRITY.txt` 如实写出这一点。
- `x64` 扫描端不在这条发布线上：`resources/native/win-x64/` 仍缺近期重编，出 64 位包前要先走 MSVC 工序补齐。
