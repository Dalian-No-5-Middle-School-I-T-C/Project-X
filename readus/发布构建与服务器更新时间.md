# 发布构建与服务器更新时间

*落笔于 2026-11-03；构建见 `.github/workflows/release-build.yml`，发版见 `.github/workflows/release-publish.yml`。*

## 这套工序解决什么

发布原本全靠手工：改 `package.json` 版本、在本机跑打包、到 Releases 页面手动传包、再回官网改文案。
断点很多，直接后果是 GitHub Releases 停在 `V1.9.6`，而主干已经走到 v2.7.x——教师按 Releases 下载拿到的是旧包。

现在把「出包 + 上新」收到仓库自己的 Actions 里，触发方式和 Rhine 的桌面构建一致：构建与发版拆开。

- **构建检测**（`release-build.yml`）：推 `main`、以及指向 `main` 的 PR，都会自动打 32 位扫描端安装包和 Ubuntu 服务端包，上传工件，不建 Release。纯文档改动（根目录 Markdown、`readus/`、`docs/`）不触发；安装包内的 `licenses/*.md` 不在忽略范围内。排除表只跳过这几类文件，新增代码目录仍然默认触发。
- **仓库里手动构建**：Actions → `Release build` → Run workflow，可只勾扫描端或只勾服务端。
- **发版**（`release-publish.yml`）：Actions → `Publish release` → Run workflow，填写 `v<版本号>`。工作流先核对标签与 `package.json` 一致、本次运行就是 `main` 的当前提交、没有已发布的同名 Release，再调用上面同一套构建。构建完成后重新核对 `main`，创建标签并上传草稿 Release，公开前再核对一次。不需要事先 `git push` 标签。
- 版本号仍以 `package.json` 为准，工作流不替你改版本号。
- 官网文案不在这里自动改：口径仍是「只更新 GitHub Release，站点由维护者自己更」。

## 怎么发一版

1. 按发版流程更新 `package.json` 的 `version` 与 `readus/CHANGELOG.md`，走 PR 合入 `main`。这次 PR 自己就会跑 `Release build`，MSI 与服务端包先在工件里。
2. 合入后打开 Actions → `Publish release` → Run workflow，分支选 `main`，标签填 `v2.7.2` 这种与 `package.json` 一致的名字。
3. 等版本闸门、构建（扫描端 32 位包 + 服务端包）、发布三条都绿。发布作业在构建完成后会重新核对 `main` 仍停在本次提交，再用 Git references 接口原子创建标签；随后创建草稿 Release 上传资产，公开前再核对一次标签与 `main`。核对不符时 Release 不会公开，失败清理会删除本次创建的草稿与标签（清理失败时保留现场供人工核对）。
4. Releases 页面出现 `Project-X v2.7.2`，资产包括：
   - `答题卡扫描端-<版本>-ia32.msi`
   - `project-x-server-ubuntu24-<版本>.zip`
   - 每条构建线各自的 `*-SHA256SUMS.txt` 与 `*-BUILD-INTEGRITY.txt`
5. 官网（宣传站 / 五中官网）的版本文案按各自仓库的检查单手工同步。

只想验证链路而不发布：推 PR，或在 Actions 里手动跑 `Release build`。两条都只上传工件。

`workflow_dispatch` 只对**已在默认分支登记**的工作流生效。这两个文件刚加进来、还没合进 `main` 时，从分支手动点 Run workflow 会 404；指向 `main` 的 PR 仍会自动跑 `Release build`。

## 32 位安装包的构建线

`resources/native/win-ia32/` 里随包的识别器与扫描桥由 `native-ia32.yml` 的 `[build-native]` 工序产出，
并由 `verify:scanner-page-timeout` 的 ⑥ 长期核对「包内件含源码现有的关键行为」。发布构建**只复用入库件**，
重编原生件仍走那条工序；CI 从 `resources/native/win-ia32/` 预置 stage 目录，再执行
`node scripts/package-scanner-win32.cjs --skip-native-build`。

预置口径与 `build-native-mingw.sh` 的产物同构：三件可执行 + `source-sha256.txt` + `licenses/`，其中 TWAIN
第三方声明从 `native/ScannerBridge/third_party/THIRD_PARTY_NOTICES.md` 补进来（随包的 `licenses/` 里本来没有
这一份，缺它等于把声明漏掉）。另外带上 `ucrtbase.dll` 与 15 颗 `api-ms-win-crt-*.dll`——**这里是按计数下限
校验的，不是靠通配拷贝成功与否**：源目录里被删掉一颗时通配会安静少拷，所以要求 `api-ms-win-crt-*.dll` 至少
15 颗、`ucrtbase.dll` 存在，并在拷完后逐个确认落进 stage（正反面都在本机跑过：15 颗通过，14 颗拒绝并退出 1）。
下限要调得有意识——它对应交叉工具集实际产出的那套 UCRT 集合。

这里要把两种「静态链接」分清：交叉构建确实把 OpenCV 与 libstdc++ 静态编进了可执行文件，但 C 运行库不是——
识别器的导入表用的是 `api-ms-win-crt-*` 那一组。UCRT 按 app-local 随包正是仓库留着这批 DLL 的原因：缺运行库的
老 32 位工作站会以 `0xC0000142` 退出（同一说明见 `scripts/stage-vc-runtime.cjs` 与 `recognition.ts`）。
真正不带的是 `msvcp140*` / `vcruntime140*` / `concrt140.dll` / `opencv_world4130.dll`：那批属 MSVC 工序
（`npm run native:build:ia32`）的布局，交叉件的导入表里没有它们，带上只会让安装包白胖约 90 MB。

打包之前先跑 `npm run verify:scanner-page-timeout`，其中 ⑥ 会核对入库的两颗 ia32 exe 确实含源码现有的
关键行为。不跑这一步就等于 CI 闭眼把仓库里现成的二进制发出去。

⑥ 只搜几颗字串，**字串还在就看不出包内件是旧的**，所以再加一道 `npm run verify:native-provenance`
（扫描端作业里，紧跟 ⑥ 之后、打包之前；该作业用 `fetch-depth: 0` 取完整历史）：
- 摘要核对：按 `resources/native/win-ia32/source-sha256.txt` 逐行哈希比对当前源码，规则与
  `package-server-ubuntu.cjs` 核对 Linux 补识别器那套一致（比对用原始字节；对不上再试 LF 归一，
  区分「CRLF 检出」与「源码真变了」两种成因）。

- 内容核对：拿 `scanner-bridge.exe` 最后一次入库的提交与 HEAD 比 `native/ScannerBridge/scanner-bridge`
  的差异；有差异说明桥接源码动过而包内件没重编，直接拒绝发布。按内容比而不是按提交时间比，
  merge / rebase 不会造成误报。

**这条作业必须同时关掉两个行尾设置再检出**：`git config --global core.autocrlf false` 与
`git config --global core.eol lf`。Windows runner 的机器级 git 配置是 `core.autocrlf=true`，
而那份清单是 Linux 上 `cmake -E sha256sum` 记的原始字节哈希。第九轮只关 autocrlf 是不够的：
`.gitattributes` 的 `* text=auto` 把这些源码判成 text 之后，检出用哪种换行由 `core.eol` 决定
（默认 `native`，在 Windows 上就是 CRLF）——第十轮的日志证明了这一点，14 个文件仍是 CRLF，
门禁本身依旧没查出真漂移。`.gitattributes` 里显式声明的 `eol` 属性优先级更高，不受影响
（`*.sh` 仍 LF、`*.bat` 仍 CRLF）。本机用同一套设置做 LF 检出后逐行比对，15 行清单全部与原始字节相符。

一个已知限制，说清楚而不是含糊过去：那份清单只覆盖识别器源码，`native/ScannerBridge/**` 一颗都不在里面，
所以桥接的历史来源只能靠上面那道内容核对兜住。要把清单补全，得改 `scripts/build-native-mingw.sh` 的摘要行——
而清单本身记录了那个脚本的哈希，改它就等于要求立刻重发二进制。因此这一步与 ia32 原生件的重编同批做，
本轮不动（本 PR 试过一次：门禁立刻把「我改了脚本」当成「包内件落后于源码」而报红，判读是对的，
代价是为一行清单改动去换现场在用的件，不值）。

32 位包的 MSI 只在 Windows runner 上编（WiX 原生运行）。曾经并列的 `ubuntu-latest` + Wine 那条线，
2026-11-03 的 CI 实测红在「Build ia32 MSI」：WiX 4 是 .NET 程序，Wine 只给了 `experimental wow64 mode`，
`candle.exe` 起来就撞上 `Wine Mono` / CLR 运行时不可用。留一条常年红的线等于给后人制造「环境问题」的借口，
所以直接删。需要在非 Windows 机器上出包时，仍按 `readus/Windows32位扫描端交叉打包.md`：macOS/Linux 准备，
Windows（本机或 VM）编 MSI，回到准备机 `--verify-msi` 复核。

### 打包脚本为此做的四处改动

- Windows 上不再直接起 `npm`：`execFileSync("npm")` 会 `ENOENT`（npm 是 `npm.cmd`，不走 shell），
  而改成 `npm.cmd` 会撞上 Node 20+ 的限制——不带 shell 时 spawn `.cmd` / `.bat` 直接 `EINVAL`。
  现在在 Windows 上用当前 `node` 直接跑官方发行版自带的 `npm-cli.js`（`node_modules/npm/bin/` 与
  `lib/node_modules/npm/bin/` 两种布局都找），找不到就明确报错；**POSIX 仍按原样走 PATH 上的 `npm`**，
  现场验证过的那条路一个字节没改。这两条错都是首跑 CI 分别撞出来的：Linux 线报 `ENOENT`，Windows 线报 `EINVAL`。
- 新增 `--skip-native-build`：只跳过 MinGW 原生编译，其余工序（前端与服务端构建、依赖装配、PE 架构核对、
  MSI 打包、包内件复核、校验清单）一步不少。它与 `--prepared` / `--verify-msi` 互斥，同时给出直接报用法错误。
  缺件时**在装依赖之前**就报错，不会跑到最后一步才发现 stage 目录是空的。
- 包内入口文件的核对改成按本机分隔符拼路径。原来写死 `"dist/scanner/index.html"` 这类正斜杠字面量，
  而 `@electron/asar` 是按 `path.sep` 切分归档路径的——在 Windows 构建机上永远查不到，会在 MSI 已经编好之后
  误报「缺入口文件」，把整条线判红。实测过：同一份归档，正斜杠查不到、`path.join` 查得到。
- Windows 主机上的 MSI 载荷核对不再走 `7za`：electron-builder 为 Windows 下的那颗 `7za` 读不出 WiX 4 包的
  压缩流，对每个文件都报 `ERROR: Data Error : xxx_f`；而同一结构的包在 macOS/Linux 上用 7za 验一直是对的，
  所以坏的是解包器，不是包。现在改用系统自己的 Windows Installer 做管理员解包（`msiexec /a`）再与 stage
  逐字节比——它必须先能把这份 MSI 解析成安装源，等于比外部解包器多证明了一层。非 Windows 主机仍走原来的
  7za 分支，现场验证过的路不改。参数拼接要注意两层引号规则不同：给 `Start-Process -ArgumentList` 的元素
  必须让双引号成为**字符串内容**（PS 单引号字面量包住一对双引号），否则引号是 PowerShell 自己的定界符，
  到 msiexec 那就没了，带空格的目录会被拆成多个参数；而同一个引号不能用在传给 cmdlet 的 `-LiteralPath` 上，
  那里多出来的引号会被当成路径字符。本机用带空格、带单引号、带中文的路径逐项验过：4 个参数不散、
  退出码能落文件。

`npm run package:scanner:win32:cross` 的行为没有改变：不带新开关时仍按原样先编原生件。

## 服务器更新时间

构建服务端产物时，`npm run build:server` 会在 `dist/server/` 下多写一份 `build-info.json`：

| 字段 | 含义 | 取不到时 |
| --- | --- | --- |
| `version` | `package.json` 的版本号 | `null` |
| `commit` / `commitShort` | 构建所在提交 | `null` |
| `commitDirty` | 构建时工作区是否有未提交改动 | `null`（未记录，不等于干净） |
| `builtAt` | 构建时刻（ISO-8601 UTC） | 缺它整份信息判为不可用 |
| `ciRef` / `ciRunUrl` | 这次发布的标签（发版时由 `release-publish.yml` 经 `ci_ref` 传入 `PROJECTX_CI_REF`），没有传就记本次 CI 的分支名 | 本地构建为 `null` |

结构版本按白名单判定：只认 `BUILD_INFO_SCHEMA`（当前为 1）。缺 `schema`、类型不对、或来自更新版本的文件，
一律判为不可用并显示「—」加原因——版本号存在的意义就是不让人按字段猜旧/新语义，宽松接受反而把它变成摆设。

git 来源只在**构建目录自己就是工作树根**时采集（`rev-parse --show-toplevel` 与实际路径比对）。
从压缩包解出来的源码若落在别的仓库工作树里，`git -C` 会往上找到那个父仓库，把不相干的提交记成
Project-X 的来源；这种情况按口径留 `null`。

服务端启动后从与服务端产物同目录读它（`PROJECTX_BUILD_INFO_PATH` 可指向别处，用于自定义部署布局）。
Ubuntu 包和解包后的 `/opt/project-x-server/dist/server/build-info.json` 随包一起走，不需要额外配置。

管理员在「控制台」页面的**服务器版本与更新时间**区块看到：版本、构建时间、构建提交、本次启动、已运行、
运行环境（Node 与平台）。两个时间各有各的用处：

- 构建时间已更新、本次启动更早 → 新包到位但服务没重启。
- 两者都很旧 → 这台服务器跑的还是旧包。
- 显示「—」→ 这次运行没有可用的构建信息（源码直跑、旧版部署包，或 `build-info.json` 缺损），
  接口同时给出原因文案。**不会**拿当前时间冒充构建时间。

接口是 `GET /api/admin/console/build`，与其他控制台端点同样要求 `system:manage`；响应只给文件名，
不给目录，`Cache-Control: no-store`。公开的健康检查 `/api/app/health` 没有加任何新字段。
「本次启动」在模块加载时定一次，是固定事实：每次请求用 `now - floor(uptime)` 反推的话，取整跨秒会让这一格
抖动一秒，管理员刷新页面会以为服务在反复重启。

构建信息按文件指纹（mtime + 大小）失效后重读，**不是进程级永久缓存**。管理员可能先打开过控制台，再把新包
拷进来；若一直返回第一次读到的内容，上面那条「新包到位但服务没重启」的判据恰恰在最该看见它的时候失效
（`no-store` 管的是 HTTP 缓存，管不到进程内缓存）。文件被删（回滚、清理）时也不再返回上一次的结果，
而是如实说明指定路径不存在。回归就按这个场景演：两次请求之间换掉盘上的文件，不清缓存、不动环境变量指针。

构建信息只认与服务端产物同目录的那一份（`PROJECTX_BUILD_INFO_PATH` 可显式指定，用于自定义布局）。
**不按 cwd 兜底**：源码直跑时仓库里那份 `dist/server/build-info.json` 属于上一次构建，把它当成本次运行的
构建时间，恰好会误导「这台服务器是不是新包」这个判断——源码直跑就该显示「—」。

回归：`npm run verify:build-info`（临时 SQLite + 真实 HTTP + 临时 git 仓库，钉住干净/脏/取不到三种状态）
与 `npm run verify:console-build-info-ui`（挂载真实控制台组件断言渲染结果），两者都已接入 CI。

## 已知边界

- **发布作业（`gh release create` 那一步）没有真跑过**：本轮不会真的打标签、也不会真的建 Release。
  已经在本机把工作流里的真实脚本抽出来，用假工件跑通了「拼装资产 → 改写清单与报告 → `sha256sum -c` →
  `hash-release-artifacts.cjs --check`（含发布用的按线改名形态）→ 生成发布说明」这段逻辑，
  但「真的建出一条 Release」仍未验证。第一次发版建议先在测试用的版本号上走一遍，或做好手工核对清单的准备。
- 标签必须指向主干**当前**那个提交：预检与发布前各核对一次 `gh api compare/main...<sha>`，只接受
  `identical`；`behind` 表示目标指向主干上更早的提交，放行的话就是把旧源码发成最新版本，正是这条检查要拦的事。
- **发布期间 `main` 前移**：构建或上传资产时主干推进，发布作业会终止，Release 不会公开，失败清理会
  删除本次创建的草稿与标签。GitHub 的 Release 公开与分支查询不在同一个原子操作里，最后一次核对只能
  缩小错配窗口；要彻底消除，需要在发布期间冻结 `main`，这是仓库治理层面的前提。
- **失败重试**：上传资产失败或发布前核对不通过时，工作流会删除本次创建且仍指向本次提交的草稿与标签，
  可以直接重跑；如果清理没完成（例如运行器被强杀），下一次预检在确认草稿带本工作流标记、标签仍指向
  本次提交后，会先清理旧草稿再重传。已经公开的 Release 不会被删除或覆盖——重发要么按发版流程升版本号，
  要么人工先删掉那份已公开的 Release；标签仍指向本次提交时会沿用，指向其它提交时再删标签
  （`git push origin :refs/tags/v<版本号>`，先确认没有别处引用它）后重跑。
- 发布作业在拼装资产时若遇到**同名不同物**的文件会直接失败，而不是挑一个发出去；清单里的路径前缀会剥到与平铺后的
  资产名一致，报告正文同样只剥前缀（**不**替换正文里的清单名——正文已经把「本机叫 `SHA256SUMS.txt`、
  Release 上按构建线改名」两种形态写清，替换反而会把叙述句改成假话），并在发布前用 `sha256sum -c` 当场对一次，
  避免把对不上的清单发出去。收件方那侧 `--check` 两种命名都认，但一个目录里只放你要校验那条线的清单。
- **服务端包必须在 LF 检出上打**。`package-server-ubuntu.cjs` 会核对随包 Linux 补识别器的源码摘要，
  而 `core.autocrlf=true` 的 Windows 工作副本会把 `native/**` 检出成 CRLF，字节摘要自然对不上。
  旧代码在此处只会抛「源码变了，请重编」，把人往错误方向引；现在会区分两种成因，CRLF 时直说是检出问题、
  要换到 LF 检出（Linux 构建机或 CI），源码真变了才维持原来的拒绝。CI 的 ubuntu runner 是 LF 检出，不受影响。
- 原生件不逐字节可复现：同一份源码两次构建出的 exe 大小与关键字符串相同，SHA256 不同（PE 头有构建时间戳）。
  核对请看包内字符串与实际运行，不要只比哈希。
- 安装包仍未代码签名（仓库不含证书），首次安装会有 SmartScreen「未知发布者」提示；发布说明与
  `BUILD-INTEGRITY.txt` 如实写出这一点。
- `x64` 扫描端不在这条发布线上：`resources/native/win-x64/` 仍缺近期重编，出 64 位包前要先走 MSVC 工序补齐。

## CI 实测结论

五跑的红是我为评审改 `msiexec` 引号时改出来的：把属性写成了整段包裹的 `"TARGETDIR=D:\out"`。
msiexec 认的是 `TARGETDIR="D:\out"`，整段包裹会让它把这一段当成未知参数，于是弹用法对话框；
非交互会话里没人点掉，`-Wait` 就一直挂着，最后被超时打死——日志只留一句 `ETIMEDOUT`，什么都没交代。
现在三处一起补上：属性形态改对；超时从 15 分钟收到 5 分钟并在报错里带上 `msiexec /l*v` 日志尾部；
`-Wait` 之后按有界轮询等载荷落盘（msiexec 会再拉一个子进程，先返回时立刻比对会误报缺件）。
参数形态用真实产品代码里的拼函数在本地回显核过：`/a "包" /qn /l*v "日志" TARGETDIR="目录"`，
带空格与中文的路径各自都是一个整体、闭合引号前没有反斜杠。没有真起 msiexec（形态错时会弹框，不该在桌面上试）。

同期 `CI` 检查：首跑红在 `verify:build-info`（`git status --porcelain` 在干净检出上输出空串，被误当成「取不到」，
`commitDirty` 全批记成未判定）；修好后 `41485839206` 全绿（Typecheck & Test、MariaDB 10.11、LLM 边车、
Electron Chromium Brotli 实机探针、Build）。`9d32ac61` 那轮（缓存失效、标签收紧、msiexec 引号分层）的
`CI` 也是全绿：`41537042623`。`ffac37d5`（msiexec 属性形态改对）这轮 `CI` 与 `Release build` 双双全绿：
`41540595057`、`41540594987`。到这里，发布链路上除「真建出一条 Release」外都在 CI 上跑通过。

留下的结论：**32 位 MSI 只在 Windows runner 上编**。Windows 侧 `7za` 读不出 WiX 4 包的压缩流
（对每个文件报 `ERROR: Data Error : xxx_f`），而同一结构的包在 macOS/Linux 上用 7za 验证一直是对的，
所以改用系统自己的 Windows Installer 解包——它必须先成功解析这份 MSI，比外部解包器更硬。
