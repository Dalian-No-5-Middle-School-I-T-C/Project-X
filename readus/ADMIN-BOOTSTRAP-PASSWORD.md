# 管理员引导口令机制与升级说明

> 适用范围：Project-X 服务端与扫描端内嵌服务（同一套 `ensureDefaultAdmin()`）。
> 关联条目：安全审查清单 R01（Codex Security Cloud，核对日期 2026-10-03）。

## 一句话结论

管理员 `admin` 不再有**任何固定口令**。首次启动时系统生成一个一次性随机口令写进
`bootstrap-admin.txt`，读它登录、首次登录强制改密；改密成功后文件自动删除，此后
无论重启多少次都不会再改写这个账号的口令。历史上公开写过的 `admin123` 已从代码、
文档和脚本里全部移除，**不能再用于登录**。

## 为什么改

旧实现有两处叠加起来是真实 P0 的机制：

1. `ensureDefaultAdmin()` 里写死常量 `admin123`，并且只要 admin 还停留在「未改密」
   的引导态，**每次启动都把哈希重置回这个公开口令**，同时吊销全部会话；
2. `/api/auth` 挂在强制改密门（428）之前，引导态会话可以直接调 `change-password`。

连起来的后果：任何读到公开文档的人都能用 `admin123` 登录一个尚未改密的部署，
改密后 `password_change_required` 置 0、引导文件删除，重启不再重置 ——
公开凭据就此被**永久转换成私有所有权**。README / SERVER-README / SCANNER-SETUP
当时还在三处公开教程化这个口令，并给出「删库重启回到 admin/admin123」的复位配方。

## 现在的机制（四种情形）

| 库的状态 | 启动时做什么 | 结果 |
|---|---|---|
| 没有 admin（全新库） | 生成 16 位随机口令，写哈希 + 写 `bootstrap-admin.txt` | 首次登录强制改密 |
| admin 已完成首次改密（标记为 0 **且**哈希验不通任何历史公开口令） | **什么都不做** | 口令、改密标记、文件状态都不变 |
| admin 仍是引导态，引导文件里的口令与库中哈希**对得上** | **什么都不做** | 口令稳定，重启不吊销会话 |
| admin 仍是引导态，但文件缺失/为空、内容等于历史公开口令，或与库中哈希对不上 | 换发新的随机口令并重写文件 | 旧口令当场失效（含 `admin123`） |
| **标记为 0，但哈希仍是 `admin123`**（评审 B4，见下节） | 按「公开口令未失效」处理：换发随机口令 + 重新要求改密 | 旧口令当场失效，并打印 `[SECURITY]` 告警 |

关键点是第三行：**引导文件（且与库对得上）是引导态口令的唯一事实源**。重启不再恢复到
任何固定值，也不再出现「每次重启把管理员会话全部踢掉」的副作用。第四行同时承担三个职责：
升级时把泄露过的公开口令作废；备份还原 / 误删文件后让系统重新可登录（自愈）；
以及避免「换了库但没换引导文件」这种文件里口令登录不进去、又永远不会变的死锁。

### 为什么第二行要多看哈希一眼（PR #312 评审 B4）

`password_change_required` 是**后来才补进 `users` 的列，默认值 0**。于是有一类库落在缝隙里：
建库早于那次迁移、管理员从未改过口令、口令至今还是 `admin123`——它的标志位是 0，
只看标志位就会把「一直没动过公开口令」读成「已完成首次改密」，直接跳过轮换。
这与 R01 对外承诺的「升级即失效，`admin123` 当场不可用」正好相反，而且这类库恰恰是
最没人管、最可能还留着公开口令的那些。

现在启动时两条都判：**标志位是意图，哈希能否被历史公开口令验通才是事实**，两者不一致按事实办
（`matchesLegacyBootstrapPassword()`，历史公开口令清单集中在 `LEGACY_PUBLIC_BOOTSTRAP_PASSWORDS`
一处维护，将来再有口令泄露就只加这一个元素）。命中即换发一次性随机口令、重新要求登录后改密，
并在服务端日志打一条 `[SECURITY]` 说明原因——不是静默改掉管理员口令。

代价要说清楚：**这类库升级后第一次重启，管理员会立刻登不进去**，必须先按下一节的位置
去读 `bootstrap-admin.txt`。不这么做的话，留着的就是一条公开凭据。

口令规格：16 位，大小写字母 + 数字 + 符号至少各一，字母表剔除易混淆字符
（`i l o I O 0 1`），用 `crypto.randomBytes` 拒绝采样生成后洗牌。
文件权限 `0600`（Windows 上 POSIX mode 可能被 ACL 忽略），与数据库同目录，随
`data/` 一起 gitignore。

## 升级影响：直接失效，没有宽限期

升级到本版本时，**行为突变只发生在两类库上**：admin 还没完成首次改密的库，以及
标志位写着「已改密」但哈希仍是历史公开口令的库（评审 B4 补的那一类，成因见上文）。

- 这两类库在下一次启动时会换发新的随机口令，`admin123` 当场失效，登录返回 401；
- 新口令写在该库数据目录的 `bootstrap-admin.txt` 里，读它登录即可；
- 真已完成改密、口令不公开在案的库（绝大多数在用部署）**完全不受影响**：口令不变、
  会话不被吊销、不会重新生成引导文件；
- 如果升级后重启服务但你没读到新口令，重启会再次换发一个（上一个失效），
  以文件里当前那份为准。

取回口令的位置：

| 部署形态 | 引导文件路径 |
|---|---|
| Windows 扫描端 / 桌面服务 | `%APPDATA%\answer-card-designer\data\bootstrap-admin.txt` |
| 源码直接运行 | `data/bootstrap-admin.txt`（与 `data/projectx.db` 同目录） |
| Ubuntu 打包服务 | `/var/lib/project-x/bootstrap-admin.txt`（跟随 `PROJECTX_DB_PATH`） |
| 自定义数据目录 | `$PROJECTX_DB_PATH` 所在目录下的 `bootstrap-admin.txt` |

Linux 服务端读取：

```bash
sudo cat /var/lib/project-x/bootstrap-admin.txt
```

拿到后立刻登录并改密；改密成功即表示该账号脱离引导态，文件会被服务端删除。

## 逃生阀：`PROJECTX_ADMIN_PASSWORD`

容器、一键部署、CI 等「读不到数据目录文件」的场景，可以在**首次启动前**设置：

```bash
export PROJECTX_ADMIN_PASSWORD='<你自己的引导口令>'
```

行为约定：

- 只作用在引导态。账号完成首次改密后，再改这个环境变量**不会**覆盖在用口令；
- 设置该变量时服务端**不写**引导文件（并清掉可能残留的旧文件，避免误导运维），
  此时口令事实源是这个环境变量；
- 变量值与库中哈希一致时不轮换、不吊销会话，重复重启幂等；
- 撤掉该变量后，若账号仍处引导态且没有引导文件，会回到「换发新的随机口令」的
  自愈路径。

基准测试工具 `tools/repair-benchmark` 就是靠这个变量把隔离部署的口令固定下来的。

## 忘记密码怎么办

- **还没改过密（引导态）**：删除数据目录下的 `bootstrap-admin.txt`，重启服务，
  会换发一个新的随机口令并重新写入文件。数据不受影响，旧随机口令失效。
- **改过密且无人能重置**：只能由其它管理员在「用户管理」里重置；若 admin 是唯一
  管理员且密码丢失，需要把 `projectx.db` 改名备份后重启重建全新库
  （**本机答题卡与成绩会随旧库一起消失**，需要时用备份文件恢复）。
- 扫描端侧的等价步骤见 [SCANNER-SETUP](SCANNER-SETUP.md) 第三节。

## 备份与还原

`POST /api/db/restore` 还原成功后会先删除当前引导文件再执行管理员引导（SQLite 与
MariaDB 两条还原分支口径一致），因此：

- 还原出来的库若处于引导态 → 换发新随机口令并写入引导文件，同时吊销该管理员的既有会话；
- 还原出来的库若已改密 → 只清掉可能泄露的引导文件，口令与改密标记都不动。

即便漏掉这一步（例如运维直接用 `mysql` 导入 dump），下一次启动也会因为
「引导文件与库中哈希对不上」自动换发口令，不会把管理员锁死。

## 下游脚本口径

任何脚本都不要再兜底固定口令，一律读引导文件；读不到就报错：

- `scripts/verify-security-critical.ts`：断言随机口令、事实源稳定、公开口令失效、
  逃生阀行为，以及「登录 → 改密 → 重启」的接管链已关闭；
- `scripts/deployment-business-smoke.ts`：优先 `E2E_INITIAL_PASSWORD`，否则读被测
  部署的 `bootstrap-admin.txt`；
- `testdata/demo-exams/scripts/verify.ts`：读引导文件，缺失即抛错（不再回落 `admin123`）。

验证入口：

```bash
npm run typecheck
npm run verify:security-critical
```
