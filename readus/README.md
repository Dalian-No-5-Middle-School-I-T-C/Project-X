> **本索引建立于 2026-10-17**，对应 `package.json` 版本 **v2.7.1**、数据库迁移 **v63**（`src/server/db/migrations.ts` 与 `src/server/db/mysql.ts` 两侧同号）。
>
> 本索引建当天以 v2.6.0/v60 为水位；同日 `git merge origin/main` 后 main 已推进到 v2.7.1，v61~v63 均为扫描端表/列，索引与各文档头的版本号据此一并对齐——版本号写旧了不只是难看，会让人拿 v60 的台账判断「这张表还不存在」。

## 四、维护约定

1. **改代码时只更新第一节的文档。** 第二节的时间点记录不回头改写——它们是「当时为什么这样做」的证据，改掉就失去价值。
2. 新增文档在第一节或第二节登记一行，并注明是否对照当前代码复核过。**没复核过就写「未逐条复核」**，不要让读者替你猜哪份是活的。
3. **`git merge main` 之后要重新过一遍本索引**：索引是分支里新增的文件，合并时不会冲突，于是 main 期间新增的文档会静默漏登记——PR #334 合并 main（#324~#333）时就出现 11 份未登记文档，已在本轮补上。这类漏项在 diff 里看不见，只能靠比对目录清单。
4. 版本相关内容（`package.json` 版本、迁移号、`verify:*` 用例数）不要写死在正文里当现状；需要引用就写明「以代码为准」。AGENTS.md 已把「旧文档中的版本号、测试通过数不代表当前状态」列为现行约束。
5. 命令、路径、环境变量名以 `package.json`、`vite.config.ts` 与代码为准；文档与实现冲突时**先修文档中确实错的那部分**，不凭旧说明改实现行为。
6. `docs/superpowers` 不是项目文档目录，不在本索引登记范围内（见 AGENTS.md）。
