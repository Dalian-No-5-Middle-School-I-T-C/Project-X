# OCR 重新识别与人工改分并发修复

日期：2026-10-15。PR：[#328](https://github.com/Dalian-No-5-Middle-School-I-T-C/Project-X/pull/328)。对应审核：[P1 本机 OCR 重试与整卡订正并发](https://github.com/Dalian-No-5-Middle-School-I-T-C/Project-X/pull/328#discussion_r4283054094)。

## 修改与结果

`runOcrOnSession` 的全部识别流程进入人工订正使用的 `enqueueScannerSubmission` 队列，涵盖读取记录、清理旧结果、原生识别、快照保存、OCR 答案、题块、质量及失败状态写入。识别中发起的人工保存会等待本次识别完成；旧草稿按修订号拒绝，新草稿在识别写入结束后保存。

抽出已持有队列时使用的失效处理函数，保留原有单独失效入口的排队行为，避免识别流程重复进入同一队列造成死锁。

新增 `npm run verify:scanner-retry-concurrency`，并加入 CI 的 SQLite 和 MariaDB 回归步骤。测试通过真实业务服务及数据库操作，在两个同步点暂停识别：原生识别尚未返回，以及订正快照已写入但 OCR 答案尚未写完。常规回归注入固定识别结果控制顺序；Windows 验证在相同同步点调用现有原生 OMR。

| 并发场景 | 验证结果 |
| --- | --- |
| 识别中提交旧草稿 | 人工保存排队；识别结束后以“已更新”拒绝旧草稿 |
| 新快照写入后提交新草稿 | 等待 OCR 答案及题块写完，再保存人工订正 |
| 修改选择题与红笔大题分数 | 机器识别 A、10 分；人工改为 B、20 分后，快照和 OCR 数据均为 B、20，正式总分为 20 |
| 人工改分先排队、重试后排队 | 人工将选择题改为 A，总分 25；已公布原卷的重试在调用识别器前被拒绝，快照和 25 分保留 |
| 原生识别失败 | 记录进入 failed，后续队列任务仍可完成 |

在隔离源码副本中，给旧实现加入相同的识别器注入接口后，新测试触发 `human save must wait while native recognition is in flight` 断言；使用修复后的实现通过。

```sh

```

生成原生识别输入需要 Python 的 PyMuPDF：

```sh
npx tsx scripts/scanner-retry-concurrency-smoke.ts --prepare-native /absolute/test-directory
python3 scripts/scanner-retry-native-image.py /absolute/test-directory
```

Windows 中设置 `ANSWER_CARD_RECOGNIZER_EXE` 指向现有原生识别器，`PROJECTX_RETRY_TEST_IMAGE` 指向生成的 `并发回归填涂.png`，`PROJECTX_RETRY_TEST_NATIVE=1`；在与 `better-sqlite3` / `sharp` 匹配的 Node 或 Electron Node 运行时中执行测试入口。Electron 模式需设置 `ELECTRON_RUN_AS_NODE=1`。本次将入口用 esbuild 打成依赖外置的 ESM，并放入现有扫描端依赖目录下，随附 SQLite / MariaDB schema 后执行。

## 第二轮 P1：订正保存与成绩入库的队列交接

审核线程：[Keep correction and admission in one queue turn](https://github.com/Dalian-No-5-Middle-School-I-T-C/Project-X/pull/328#discussion_r4283289230)。

`saveSessionCorrection` 原先在订正事务完成后释放队列，再重新排队入库。已等待的重试预览可能在中间读到“已订正但回执仍待处理”，取得重试资格。现将该卷的订正保存及 `processScannerSession` 入库合并为同一次队列任务，并复用队列内处理函数，保留原有版本、名单、撞号和逐卷入库检查。

新增回归先通过实际扫描保存和撞号流程撤回 91002 原卷，再把撞号新卷订正为 91003。测试在原卷订正事务提交前暂停，通过真实扫描鉴权和 HTTP `/api/scanner/session/:sessionId/retry` 发起重试，确认其已经读到记录并等待预览，再释放订正事务。

旧实现在隔离源码副本中返回 200，触发“应拒绝重试资格”的断言；修复后重试返回 409“此答题卡未失败”，原卷回执保持 saved，订正快照、OCR 答案均为选择 B / 大题 20 分，正式总分保持 20。该场未公布且没有公布历史，排除了已公布原卷保护对本用例的影响。

本轮通过：本机 SQLite 新旧实现对照、Ubuntu amd64 / MariaDB 10.11 专用空库 `projectx_scanner_batch_handoff_20261015`、Windows 原生 OMR 的同一并发脚本。原扫描批次、整卡订正、异常卷回归以及类型检查、Web / 服务端 / 扫描端构建均通过。

## 同轮 P2：大考组选项的软删除成员过滤

审核线程：[Exclude deleted members from ladder options](https://github.com/Dalian-No-5-Middle-School-I-T-C/Project-X/pull/328#discussion_r4283289235)。结论：当前代码已过滤，审核为误报。

列表使用 `EXAM_NOT_SOFT_DELETED_SQL` 按 `e.id` 过滤，详情使用 `GROUP_MEMBER_NOT_SOFT_DELETED_SQL` 按 `egm.exam_id` 过滤；列表的 JOIN 条件 `e.id = egm.exam_id` 保证两种写法等价。

新增 `npm run verify:ladder-options-soft-delete`，通过真实学生登录与 HTTP 列表、详情接口验证以下行为；保留两条组成员关系，确保测试实际覆盖软删除：

- 已删除的未公布成员不会隐藏有效大考组，详情返回 200 和本人 50 分。
- 学生仅参加过已删除成员时，列表不显示该考试及大考组，详情返回 403。
- 恢复为有效但未公布的成员后，大考组按公布门槛隐藏，详情返回 403。
- 所有成员均删除时，列表不显示该组。

该回归在 SQLite 及原 Ubuntu / MariaDB 专用空库 `projectx_scanner_batch_ladder_delete_20261015` 均通过，并已接入两种数据库的 CI。P2 对应的产品查询保持现有实现。本轮日志保存在忽略目录 `ignored/production-flow/evidence/` 的“订正入库交接”及“天梯软删除”文件中。
