# 扫描端胶囊（Windows 扫描端全链路）

> 改扫描端前只读这一篇即可拿到进程模型、CLI 契约、上传协议、异常卷与打包副作用。
> 事实基线：`ec5b411`（**2.7.1**），2026-10-17 逐项核对。**与代码冲突时以代码为准**；全局视角见 [项目胶囊](项目胶囊.md)。
> 边界：扫描仪与 OMR 只能 Windows 真机验收；Linux CI 覆盖的是纯逻辑冒烟（§13）。

## 1. 进程模型（最容易被误解的一点）

- `electron/` 下**只有 `main.cjs`**。它 `await import()` 加载 `dist/server/index.mjs` 并调用 `startServer()`，**Express 与 Electron 同进程**（main.cjs:153-175），不是子进程，也没有 IPC 层的「桌面端 ↔ 本地服务」协议。
- `process.chdir(userData)`（:135-149），`userData = %APPDATA%\answer-card-designer`。因此**库与图片都在 userData 下**，直接 `node dist/server/index.js` 起的服务用的是 cwd —— 两者数据不互通。
- 主进程注入的环境变量（:160-163）：`PROJECTX_ENABLE_SCANNER=1`、`ANSWER_CARD_DATA_DIR=<userData>/data/answer-card`、`PROJECTX_DB_PATH=<userData>/data/projectx.db`。端口 `PROJECTX_ELECTRON_PORT` 默认 5174，占用时回落随机端口（:167）。
- 日志：`userData/logs/main.log`（:47）。**console 被接管**（:111-113），服务端 `console.log` 会逐行进 main.log —— 这是现场取证的主通道。窗口加载 `http://127.0.0.1:<port>`（:391-392）。
- 渲染层两个入口：`client/main-scanner.tsx`（错误兜底 overlay :13-38、主题/皮肤预设 :40-56、挂载 `ScannerApp` :58-68，**只引 app.css**）与 `client/ScannerApp.tsx`（登录→选卡→工作台状态机；选卡时 `fetchCardDetailSynced` 校验卡片版本，`stale` 分支按安全 R35 弹确认让老师显式选择「离线继续」，远端新建的卡先 `importCardLocally` 幂等入库，见 :141 起）。

## 2. 「本地扫描」与「上传到远端」是两件事

- 扫描端**永远连自己的内嵌服务**（loopback）。远端服务器只是**上传目标**，模式与地址存 localStorage：`projectx_server_url`、模式 key（`client/lib/scannerMode.ts:11,52-110`，`getScannerMode()` 默认 `local`）。
- 两个开关别混：
  - `PROJECTX_ENABLE_SCANNER` → 本机 TWAIN/原生能力。`scannerEnabled()`（`server/index.ts:711-721`，另含 `PROJECTX_VARIANT=teacher-scanner`）。关闭时 `/sources` `/scan` `/progress` 返回 404，但图片预览等纯文件路由仍可用。
  - `PROJECTX_ENABLE_SCANNER_CLIENT_API` → **服务端**接收扫描端上传的 API。只被 `src/server/lib/scannerClientAccess.ts:12` 读取；Ubuntu 包在 `scripts/package-server-ubuntu.cjs:119-120`（systemd unit）与 :97（启动行）注入默认 `0` / `1`。门控点在 `server/index.ts:1073-1074`（关闭时 :1076/:1082 返回 404）。`isScannerClientOrigin()`(:20) 只允许 http + `127.0.0.1|localhost|[::1]`。
- 上传端点鉴权用 `dualAuth`（`src/server/middleware/scanner-auth.ts:13`，API Key 或 Bearer 均可），TWAIN 端点走 `scannerAuth` + 会话/考试范围校验（`middleware/scanner-scope.ts:213/362/380`）。
- **没有扫描配置文件**。`config.yml` 只有 `database` 段。

## 4. 两个原生二进制的 CLI 契约

**scanner-bridge.exe**（`twain-bridge.ts:521-544`，有子命令）

```
scanner-bridge.exe scan --source <name> --dpi <n> --mode <gray|color|bw> --size <paper>
  --output <dir> --prefix <p> --max-pages <张数> [--page-timeout-ms <ms>] [--duplex] [--show-ui]
```

- `--max-pages` 单位是**物理张**；`--page-timeout-ms` 是等下一页（ADF 送纸）的空闲超时。路由层恒传规范化值（默认 60s），**不要依赖 exe 内部默认**（旧包是 15s）。
- 设备无响应 / 零页失败以「结构化 JSON + 非零退出码」返回；`runBridge` 只要 stdout 有内容就 resolve（不抛错），所以这类失败必须在调用侧显式判定。
- **stderr 逐行原样进日志**：`logBridgeStderr()`（:330-336）加 `[scanner-bridge]` 前缀，Electron 下经 console 接管写进 main.log。CAP_XFERCOUNT 协商、每页 pending 张数、FEEDERLOADED 复核、等纸超时原因**只在 stderr**，排查「只扫一张」先看它。
- `describeBridgeFailure()`(:339) 把常见 Windows 退出码翻成中文，含 `0xC0000135 STATUS_DLL_NOT_FOUND`（v2.5.6 起运行库随包分发，所以缺 VC++ 不再是唯一解释）。

**answer-card-recognizer.exe**（`recognition.ts:86-101`，无子命令）

```
answer-card-recognizer.exe --identity-mode <m> --image <jpg> --layout <json> --page <n> --dpi <n>
  [--debug-dir <dir>] [--crops-dir <dir>]
```

- 旧 exe 不认 `--crops-dir` 时按 `Unknown argument: --crops-dir` 自动降级重试（`isCropsDirUnsupportedError` :103-107）。
- 二维码/学号闸门：`validateIdentity()`（:218）失败抛 `CardIdentityError`（HTTP 422，`CARD_IDENTITY_REJECTED`）。
- 默认彩色有**三处各自独立的默认值**，改默认必须同改：UI `ScannerPanel.tsx:92`、路由 `scanner/index.ts:134`、落库 `database/scan-store.ts:89`（native 侧像素类型映射在 `twain_controller.cpp:998-1000`）。

## 5. exe 解析优先级

- `resolveScannerBridgeExe()`（`twain-bridge.ts:181-198`）：`SCANNER_BRIDGE_EXE` → `<resources>/native/<archDir>/scanner-bridge.exe` → `<root>/resources/native/<archDir>/...` → `<root>/native/ScannerBridge/scanner-bridge/{Win32|x64}/{Release|Debug}/...`；找不到抛错并列出全部候选路径。`archDir` 由 `process.arch` 决定（ia32→`win-ia32`；`nativeBuildPlatform()` :176-178 把 ia32 映射为 `Win32`）。
- `resolveRecognizerExe()`（`recognition.ts:33-51`）：`ANSWER_CARD_RECOGNIZER_EXE` → `resources/native/win-<arch>/answer-card-recognizer.exe` → `native/AnswerCardRecognizer/<平台>/{Release|Debug}`。
- Linux 补识别走**独立解析器**：`resolveCorrectionRecognizerExe()`（:200）只认 `resources/native/correction-linux-x64/answer-card-recognizer`，缺文件即报「请安装完整的 2.7.0 或更新版本 Ubuntu 服务端包」。

## 14. 扫描后处理页（v2.7.2）

**入口**：`ScannerWorkspace` 的 `onScansComplete` 上抛 sessionId（`ScannerWorkspace.tsx:230-234`）→ `ScannerApp` 切 `postprocess` 屏（`ScannerApp.tsx:24, 124-134`）。页头「返回扫描」回工作台续扫，第二批会话累加进同一队列（`postSessions`）；**换卡时必须清空 postSessions**，否则拿另一张卡的 sessionId 去读结果。

三视图互斥渲染（右上角 `SegmentedControl`，不是三栏同屏）：

| 视图 | 职责 | 实现 |
| --- | --- | --- |
| 扫描结果 | 本批全部卷子的方块网格 / 列表、考号搜索、全部·正常·异常筛选、多选删除 | `components/scanner-postprocess/PostprocessResultsView.tsx` |
| 卡查看与改分 | 左画布点选 + 右列按题改分（客观=选项下拉或 chips，主观=分数输入），同一份 correction 文档驱动，**无模式切换** | `PostprocessCorrectionView.tsx`、`CorrectionCanvas.tsx`（与 §9 整卡改分弹窗共用） |
| 异常处理 | 队列式：考号重复 → 考号问题 → 缺页 → 识别存疑 →（`other` 兜底），处理完自动跳下一条，可暂时跳过 | `PostprocessQueueView.tsx`（五个面板） |

- **分类只看结构化信号**，不解析 `failure.message` 文案：`conflicts` 非空→重复、`studentId===null`→考号问题、缺 `layoutPage`→缺页、`needsReviewCount>0`→存疑，都不是才 `other`。逻辑集中在 `shared/scanPostprocess.ts`（组视图模型、队列推导、删除护栏、`replaceScopedSelection`）。
- 表格里改一题必须走 `replaceScopedSelection()`：**只替换该题作用域内的格**；直接整页覆盖 `selected` 会把同页学号和其他题的填涂一起抹掉。格选择逆运算在 `shared/correctionCellSelect.ts`（`evaluateScoreCells` 位规则的反解，冒烟用往返断言钉住）。
- **通道唯一为本地**（`postprocessChannel.ts`）：本页持的是本地 TWAIN sessionId，而 `/api/scanner/upload/*` 认 `job.remoteSessionId`，两者不同域；`scannerUploadManager.requestJob()` 对已收尾的 job 直接 reject。远端语义只由 `queueGroupUpload()` 自建上传任务承担，与 §8 直扫上传同构——别在这里新造远端读写。
- 批结果口径跟 `ScannerPanel.readResults` 保持一致：图片去向为远端时 `GET results?previewOnly=1`，仅本地时 `POST validate`。**不要无条件 validate**——它会为本机每份卷写 pending 回执，污染 §9 的待处理队列并架空删除护栏。
- **仅本地模式的入库入口在本页视图 1**：自动跳页会卸载 `ScannerPanel` 的 done 视图，原来那个「保存成绩」按钮随之消失，而 `POST validate` 只演算不落库——不接回来就是「一批正常卷看起来正常、成绩表里却没有」。视图 1 工具条的「保存成绩入库」走 `POST /api/scanner/session/:sid/results`（save 模式，与原 `saveSuccessful` 同端点），只在未开远端上传时显示。
- **视图 2 一组成只许保存一次**：`saveSessionCorrection` 在 PUT 末尾用 `mode="save"` 顺带接纳该组，之后同一条通道明确拒绝（`此卷已入库或已作废，请从成绩修改进入整卡改分`，`services/scanCorrection.ts:189`）。保存返回 `saved` 后界面必须锁住并指向 Web 成绩修改；只刷新 revision 仅解决了乐观锁那一层。
- 补传护栏（D12）：**只有「本页亲眼见过它异常」的组才允许补传一次**。判据要连 `failures[].conflicts` 里的副本一起记：重卡中被「保留」的那份往往只出现在 conflicts 中，漏了它，定性完仍然不会补传（另一份已作废，服务器再也没有这份成绩）。正常组在扫描完成时已被 `ScannerPanel.queueSuccessfulUploads` 排队，再建一个远端会话就是同考号第二份回执 → 服务端 conflict → `withdraw()` 删 `student_scores`/`question_scores`（`scannerSubmissions.ts:121-141`）。别拿 `scannerUploadManager` 的任务列表当判据：它是内存态，进度卡关闭（`dismissJob`）或扫描端重启就查不到，判据失效的方向恰好是「误重传」。
- 删除按会话逐一下发：`groupId` 只在单个 session 内有意义（`session-results.ts` 的 `groupIndex`），续扫后两批会出现同名组，混在一起删会删掉另一批的卷子；视图 1 的选择集与 React key 也用 `sessionId/groupId`。组内存在 saved/held/conflict/roster 回执时必须 `force`，否则 409 点名 `blocked`；整批删除走 `writeScannerSession` 的同一事务（逐条 `deleteScanRecord` 中途失败会留下半删的组，validate 随即报成新的缺页异常）。**远端通道没有删除端点，也不要新造**。
- 读扩展：`GET /api/scanner/scan/:sessionId` 追加 `examId`，供视图 3 改考号查花名册（`GET /api/exams/:examId/participant-search`）。本机定不出考试归属时返回 null，前端降级为纯手输 +「该考号不在应考名单」提示；该提示只在名单查询真的成功后判定，避免查询失败被误报成缺考。
- 验证：`verify:scanner-postprocess`（纯函数）、`verify:scanner-postprocess-delete`（端点 + 回执护栏，隔离 SQLite / MariaDB 可切换）、`verify:scanner-postprocess-ui`（jsdom 真实挂载三视图：画布↔表格双向即时同步、409 二次确认、考号逐位写格、补传卡版本、队列清零）；CI 跑 `verify:scanner-postprocess-all` 一条汇总。
