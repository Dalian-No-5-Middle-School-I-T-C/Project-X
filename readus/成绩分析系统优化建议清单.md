## 二、P0 —— 高价值低成本 / 高风险，建议立即做

### 1. 消除分析链路 N+1 与逐行子查询 【复杂度：低】
- **问题**：
  - `AnalysisRepository.ts` L198-201：每个分数段发一条 COUNT（150分卷/10分段 = 15 条查询），且 `getPreviousExamComparison`（L258-261）会调两次 `getExamOverview`，查询量翻倍
  - L207-215 `getClassScoreSummaries`：逐班串行 `await getScoreSummary`
  - `exam-groups-analysis.ts` L54-78：每科发 3 条查询（满分/标准差/及格优秀），9 科大考 = 27 条
  - L302 `getStudentRanking`：SELECT 内嵌 2 个相关子查询，随学生数线性放大
- **改动思路**：分布统计一次拉 `total_score` 列表后 JS 分桶（`getScoreSummary` L219 本来就在拉同一份数据，可合并复用）；班级汇总改一条 `GROUP BY class_id` + JS 算分位数；每科 3 条合并为 1 条聚合；排名子查询改 `LEFT JOIN + GROUP BY`。全部沿用 `classFilter` 模式不碰方言专属语法
- **收益**：查询量下降约 80-90%，纯查询层改动，行为不变，风险最低

### 2. 扫描入库事务化与批量写入 【复杂度：低-中】⚠️ 数据正确性风险
- **问题**：`scanner/index.ts` `persistScannerResultToMainDb` L68-91 逐题串行 `await db.run`，无事务。一次 500 人 × 30 题的扫描 = 1.5 万条独立写；中途崩溃会留下 `student_scores` 已写、`question_scores` 缺行的脏数据，**直接污染后续全部分析**（难度/区分度/逐题统计）
- **改动思路**：每个学生（或每场考试）包进 `db.transaction`（`SqliteAdapter.transaction` L147-160 已实现）；better-sqlite3 的 prepared statement 在事务外 prepare 一次、事务内复用；排名重算改为整批扫描结束后触发一次（若当前每张卡都触发 `recomputeExamRankings`）

### 3. 学生个人跨考试成长曲线（功能）【复杂度：中】
- **价值**：`StudentScoreDetail` 目前只看单场考试；"这个学生本学期数学走势、年级排名是否持续下滑"是教师和家长最高频的问题，现有功能缺口中价值最高
- **改动思路**：
  - 后端：新增 `GET /api/analysis/students/:studentId/trend`；`AnalysisRepository` 新方法参照 `getScoreTrend`（L282）按考试时间排序模式，改按 `student_id` 过滤；排名优先复用 `rankingUpdate.ts` 已落库结果，避免逐场重算
  - 前端：`StudentScoreDetail.tsx` 新增"成长趋势"区块，折线图复用 `AnalysisCharts.tsx` 现有组件
  - 图上双线：**得分率**（解决不同满分不可比）+ **年级百分位**；缺考场次画断点而非零分
- **注意**：一次查询拉该生全部历史成绩 + 每场考试的年级统计，避免循环查询

### 4. 临界生（踩线生）名单（功能）【复杂度：低-中】
- **价值**：高中年级组核心日常工作——及格线/优秀线/自定义"模拟批次线"上下 ±N 分的学生名单，直接决定培优补差名单
- **改动思路**：
  - 新端点 `/exams/:examId/borderline-students`；数据完全复用 `getStudentRanking`（L299）已有的总分+排名，只是加过滤
  - 考试组场景复用 `getCrossExamTotal`（L149）已算好的 rows（含 totalScore/gradeRank）
  - 阈值线三种来源：百分比线（复用 `getAnalysisThresholds` 配置体系）、绝对分数线、考试组总分折算线
  - 输出按"距线分差"升序，支持班级筛选，导出复用现有 XLSX 通道（`export-scores.ts`）
  - 前端挂在 `ScoreDetailPage` overview Tab 加入口卡片

## 三、P1 —— 重要，第二批实施

### 5. AI 学情分析异步任务化 【复杂度：中】
- **问题**：`analysis.ts` L505-515 `fetchLlmClient(..., 120_000)` 同步阻塞最长 120 秒，期间 HTTP 连接占死、用户无法取消、无进度反馈
- **改动思路**：单机不引入消息队列——用"SQLite 任务表 + 内存串行队列"：
  - POST 创建任务立即返回 `taskId`（表 `ai_analysis_jobs`: id/exam_id/class_id/status/result/error/created_at）
  - 后台串行 Promise 队列执行（并发=1，天然防重）
  - 前端轮询 `GET /ai-analysis/jobs/:id`，或复用扫描已有的 WebSocket 通道推完成事件
  - 落库的任务结果顺便成为 AI 分析结果的持久缓存
  - 注意 Electron 退出时未完成任务标记 failed

### 6. 分析结果缓存与精准失效 【复杂度：中-高】
- **问题**：除阈值内存缓存（`analysisConfig.ts` L59/L71）外，所有分析每次全量重算；用户切换班级筛选、来回切 Tab 全部重来
- **改动思路**：
  - 一阶段：纯内存 LRU（Map + 条数上限约 50 个 examId+classId+阈值版本 组合，ia32 内存有限必须设上限），单机单用户足够
  - 二阶段（可选）：SQLite 物化表（JSON 存 overview/逐题分析结果），支持重启后秒开
  - **失效钩子是主要工作量**：`score-editing.ts` 改分、扫描入库完成（建议 2 的事务提交点）、`answer_overrides` 变更、阈值更新时按 examId 精确清除

### 7. 偏科预警（功能）【复杂度：中】
- **价值**：原始分跨科目不可比（数学 110 和语文 110 含义完全不同），用 Z 分识别"单科显著低于本人整体水平"的学生；班主任和年级组刚需
- **改动思路**：
  - Z = (个人分 − 年级均分) / 年级标准差，逐学生跨科比较，Z < −0.8（阈值进配置）即预警
  - 跨科数据复用 `getCrossExamTotal` 的考试集合解析逻辑（L149-158）；Z 分计算模式成绩表已有（离差/Z分/百分位三模式）可参照
  - 前端：个人各科 Z 分条形图 + 班级名单表，挂 class-compare Tab 或独立卡片
  - 无考试组时降级为单场考试的客观/主观题块对比

### 8. 知识点半自动标注（功能，解锁知识点分析链路）【复杂度：第一步中 / 第二步中-高】
- **问题**：`knowledge_points`（建表 L251）完全依赖人工标注——无标注则 `KnowledgeAnalysisInline` 的知识点弱项分析形同虚设，这是整个知识点功能的瓶颈
- **改动思路**：两步走：
  - 第一步（低成本高杠杆）：内置按学科维护的静态知识点词典（关键词 + 题型规则），对题干文本匹配出候选知识点，弹人工确认界面批量勾选
  - 第二步（可选）：接入现有 llmclient 通道批量预标注（复用建议 5 的异步队列），人工只纠错
  - 标注结果仍写 `knowledge_points` 表，**下游所有分析代码零改动**

### 9. 索引补齐与双方言函数审计 【复杂度：低】
- **问题**：`student_scores`（L516）/`question_scores`（L534）是所有分析的命中表，复合索引覆盖情况未确认；SQL 中 `date()`、`IFNULL`、`COALESCE` 混用，MariaDB 方言下需统一审计
- **改动思路**：
  - 用 `EXPLAIN QUERY PLAN`（SQLite）/ `EXPLAIN`（MariaDB）跑核心查询确认索引命中
  - 缺失则补 `CREATE INDEX IF NOT EXISTS`（双方言语法一致，成本低）：候选索引 (exam_id, student_id)、(exam_id, question_number, score_type)
  - 整理一张"双方言安全函数清单"（如统一 COALESCE），后续新 SQL 对照
- **定位**：防御性投资，建议和建议 1 一起做

## 四、P2 —— 改进，按需排期

### 10. 班级知识点掌握雷达对比（依赖建议 8）【复杂度：中】
- 跨班对比 Tab 已有雷达图但维度是总分；"3 班函数弱、5 班立体几何弱"这种知识点维度对比才是教研活动的核心素材
- 一条 `GROUP BY class_id, knowledge_point` 聚合（得分率 = SUM(score)/SUM(max_score)）；前端复用雷达图，轴改为知识点
- 标注不全时按已标注题目子集计算，UI 显示覆盖率提示（如"覆盖 62% 题目"），避免误读

### 11. 学生错题本生成与导出 【复杂度：中】
- 数据源 `question_scores`（L534）过滤 `score < max_score * 0.6`（阈值进配置）
- 分两步：先出 XLSX 题号+得分清单（不依赖题干）；再升级含题目全文的 PDF 练习卷（隐藏答案版 + 答案版），PDF 用 Electron 自带 `printToPDF`（零新依赖，ia32 友好）
- 题面内容需先确认答题卡定义中的题干/图片存储位置（`CardRepository` 相关）
- 建议 8 落地后可按知识点聚合错题

### 12. SqliteAdapter 事件循环阻塞缓解 【复杂度：低（测量方案）/ 中-高（worker 方案）】
- `mysql.ts` L125-146 better-sqlite3 同步调用包 async。诚实评估：单机单用户、单条查询 μs-ms 级，**实际影响中等，优先级不必最高**
- 真正的风险点：`transaction`（L147-160）里 `await fn(this)` 在 BEGIN/COMMIT 之间允许穿插异步——当前安全但未来误用真异步会破坏事务原子性
- **先测量再优化**：给 `all/get` 加耗时日志找 >50ms 语句（做完建议 1、6 后大部分会消失）
- worker_threads 方案需**先在 ia32 环境验证 better-sqlite3 原生模块编译**，风险高缓行；同时给 transaction 加注释约束"fn 内禁止真异步"

### 13. 学生个人成绩报告单 PDF（功能）【复杂度：中】
- 家长会/学生手册场景——单页 A4：总分与排名、各科雷达、薄弱知识点、相对上次进退，一键生成
- 前端复用 `AnalysisCharts.tsx` 组件渲染隐藏页面 + Electron `printToPDF`；数据复用建议 3 的成长曲线端点 + 单场分析接口
- 批量生成（全班）必须串行 + 分批，控制 ia32 内存峰值

## 五、P3 —— 锦上添花

### 14. 年级间同类考试对比 【复杂度：中】
- 同一模板卷跨年级（如高一高二同卷月考）的均分/标准差/难度对比，命题组视角；使用频率相对低
- 复用 `getExamFilterItemsByIds`（L94）与 `getScoreTrend`（L282）的聚合模式，按相同 `card_id` 聚合各年级统计，柱状图对比

### 15. 学科命题质量趋势追踪 【复杂度：低-中】
- `computeQuestionAnalysis`（L336）已算出难度 P / 区分度 D，把历次考试的 P/D 画成趋势线/散点，帮命题老师发现"卷子区分度持续 <0.3"这类问题
- 零新计算逻辑，建议 6 缓存落库后成本更低；前端折线/散点复用现有 Chart.js 封装
