## 修改内容

### 学生天梯列表

新增只读 `/api/ladder/options`，供学生天梯选择范围。考试需满足本人在冻结/显式名单内或已有成绩、成绩已公布、未软删除；大考组需包含本人参与的考试，且所有有效成员均已公布。返回选择器所需的名称和 ID 等最小字段。学生前端改用此接口，教师继续沿用现有入口。

回归覆盖本人范围、未参与范围、撤回公布后的隐藏，以及教师管理列表继续拒绝学生访问。真实 MariaDB 部署中另核对：考试 5 / 大考组 3 公布前隐藏，公布后出现；诊断用未公布考试未进入学生列表。

### 扫描主表刷新

导入图片与上传任务按物理页和正反面关联。后台完成、异常卷订正与重新保存后，主表接收最新学号、状态、逐题明细及分数，并更新 CSV 数据；窗口切回和每 30 秒定时刷新可读回教师端的后续改分。已关闭上传浮卡后，表中已更新的数据继续保留。

完成通知只刷新对应任务；定时及窗口切回刷新当前批次。刷新请求去重、合并，旧请求晚到时不覆盖更新的响应；未上传完整的失败页继续保留原失败状态和重试入口。

结果查询从教师最新保存的订正快照读取填涂，再生成逐页明细与汇总。该读取直接复用已有结果接口，不触发保存，不调用整卡订正接口，不占用人工订正接口的并发或频次限额。测试期间曾发现整卡订正接口限流、原始上传识别与教师订正快照不同步，两处均已在最终实现中解决。

### 考试名称

成绩分析进入详情时按选中的考试 ID 读取正式元数据，避免依赖未加载的工作区考试缓存。异步响应按当前选中 ID 隔离；详情页、改分页和导出弹窗取得相同的考试名称和学科。

## 最终 50 张卡流程

环境沿用上一轮：Ubuntu ARM64 内核中运行 amd64 Ubuntu 24.04、Node x64、MariaDB 10.11 和 Nginx；Windows 11 ARM64 中运行 ia32 原生识别器及真实扫描前端。使用程序正式 API 建档、程序导出的 PDF 填涂图片、Windows Edge 实际控件操作和原生 OMR。

1. 重新导入 50 张卡，三对撞号和一张空学号；正式成绩 43 份，6 张撞号卷待处理，空学号卷保留在扫描端。
2. 在扫描前端订正 10002、10004，并逐份保存新旧卷；达到 47 份，主表四张卷学号和状态立即更新。
3. 老师在整卡改分中把 10008 第 4 题 A 改 D、大题 18 改 25，总分 33 改 45。核对持久化、排名，以及扫描表的 45/50 和更新后的明细。
4. 老师在考试管理公布 47 份成绩；10008 学生逐题查分通过，考试及大考组进入学生天梯列表。
5. 保持 10006 学生成绩页打开；在扫描前端订正并保存最后一对撞号，再订正空学号为 10007 并重试上传。
6. 正式成绩达到 50 份，撞号清单和主表异常均为 0，公布状态保持为 1；50 人总分、竞争排名及统计逐人核验通过。

学生自动更新证据：北京时间 **19:38:56** 的查询尚无考试 5；**19:40:26** 的后续自动查询出现考试 5、21 分。期间没有点击刷新或重新登录。此时间区间还包含等待执行最后补录的时间。

最终成绩总和 1237，接口均分 24.7，最高 45，最低 10。教师下载的 Excel 包含 50 条学生行，10008 的总分/客观分/主观分为 45/20/25。教师最终页面 39 个业务请求、学生最终页面 21 个业务请求全部成功，前端异常列表均为空。

扫描 CSV 另核验 50 行均为正常、异常数均为 0，10008 为 45 分。最终构建已同步到两台虚拟机；浏览器测试会话和临时文件传输服务已关闭，隔离应用服务及测试数据保留。

诊断考试 3、4 保持未公布；最终验收以考试 5 为准。调试期间的截图超时、服务更新期间的短暂查询失败及改分快照读取失败留有原始记录，随后在稳定服务上重新操作并核验通过。
