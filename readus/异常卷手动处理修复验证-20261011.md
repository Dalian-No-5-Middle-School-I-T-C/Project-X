# 异常卷手动处理修复验证

日期：2026-10-11。修复分支：`codex/fix-scanner-manual-recovery`。

## 问题与修复

远程异常卷面板的“重新保存此会话”原先向 `/api/scanner/upload/sessions/:sessionId/complete` 发送空请求体，服务端要求 `cardVersion`，因此手动保存被 400 拒绝。现在保存由上传管理器执行，使用目标会话自己的答题卡版本及原服务器凭据。版本回执按服务器、答题卡和会话保存到浏览器本地存储，关闭任务或重建队列后仍可读取，服务端原有版本校验继续执行。

同一组冲突证据原先在每条失败记录及多个上传任务中反复出现。现在本地汇总和远程浮层按会话、分组去重；每份原卷保留一个查看、订正和保存入口。关联旧任务只接收属于它自己的失败分组，已有其他失败也予以保留。

手动保存后通过 GET 刷新同一服务器、凭据、答题卡的相关任务。刷新包含部分保存成功后的状态，直接反映服务器结果，不再次提交 complete。订正后的新卷即使已不属于重复学号，也会保留未保存原卷的操作入口。普通入库失败也可继续订正；后端拒绝改动已保存的分组。重复卷面板收口到原卷订正操作，上传失败与保存失败的重试文案分别显示“重试失败页”和“重试保存”。

- `npm run verify:scanner-upload-manager`：macOS 与 Parallels Windows 11 的 Node 24 均通过。覆盖目标会话版本、关闭旧任务、队列重建、服务器隔离、普通入库失败订正、相关任务刷新及未保存原卷入口。
- `npm run verify:scanner-batch-results`：隔离 SQLite / HTTP 回归通过。
- 同一批 HTTP 回归在 Parallels Ubuntu 24.04 内的 Node 24 容器与真实 MariaDB 10.11 容器上通过。使用独立空库，未连接业务数据库。
- `npm run verify:auth`、`npm run verify:security-critical`：通过。
- `npm run build:web`、`npm run build:scanner`、`npm run build:server`：通过。Vite 提示较大的构建块，构建正常完成。
- `git diff --check`：通过。

HTTP / 数据库回归覆盖：重复学号撤回旧成绩；新旧原卷保留；订正新卷；首次订正输错学号后保存失败；同会话其他有效卷先保存；再次订正失败卷；禁止改号已保存的同组卷；远程恢复旧卷；重复保存保持一条有效回执；旧版本或缺少版本仍被拒绝。

Windows 11 / Edge 中加载的是本分支的实际 React `UploadProgressCard` 和 `ScannerConflictCards`。界面测试使用隔离的请求桩，实际点击了订正和重新保存按钮：三份原卷只显示三行；保存仍返回 409 时保留全部证据；订正两份新卷后先保存旧卷，再保存新卷；中间两份待保存的新卷仍可查看和保存；最终两个任务均完成。整个场景保持两个会话、三次图片上传和五次明确触发的 complete，没有额外入队或重传。界面截图保存在忽略目录 [异常卷订正回归.png](../ignored/scanner-recovery-validation/异常卷订正回归.png)。

CI 已加入上传管理器回归，并在 MariaDB 任务中创建独立扫描回归数据库运行同一批 HTTP 回归。

## 验证边界

Windows 界面回归使用请求桩；Ubuntu 回归调用真实认证路由和 MariaDB，使用预置识别记录。此次没有运行 Windows 原生 OMR、TWAIN 或真实扫描仪，也没有连接生产服务。

旧版本应用从未记录版本、且原上传任务已丢失的历史会话，无法可靠推断其原始答题卡版本；保存会明确提示版本未知。新增版本回执可保留本次修复版本创建的会话，不能重建已经丢失的历史指纹。
