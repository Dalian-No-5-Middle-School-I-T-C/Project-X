## 一、功能概览

1. **成绩公布门控（v41）**：批改完成后成绩**默认不公布**（`score_published=0`），教师结考后手动公布（=1）、可撤回（=2）；学生端所有成绩接口只认 `score_published=1`。
2. **发布操作与审计（v42）**：单场/批量公布、撤回（含原因），`exam_publish_events` 全程审计；改分/改答案/仲裁/网阅/赋分重算等任一写分路径在**同一事务**内自动撤回公布（`markScoreMutated`）。
   > **已被 #326 改为策略开关**（§七）：撤回与否由全局设置 `auto_unpublish_on_score_change` 决定，**默认关闭＝写分后保持已公布**，开启才撤回并写 `unpublish` 审计。
3. **发布完整性校验（P1-1 / P1-2）**：公布前必须「应考集合 ⊆ 已评分集合」；应考名单来自管理员显式名单或年级/班级名册快照（`exam_participants`，v47/v48 迁移）；**任何情况不再有「仅校验非空」退路**。
   > **已被 #326 放宽**（§七）：名单快照仍照常固化与展示，但**不再是发布门槛**——只要该场有 ≥1 条成绩即可公布已有成绩。

## 二、⚠️ 破坏性变更（合入前必须知晓）

### 变更 A：成绩默认不公布 → 学生端可见性变化

| 影响面 | 变化 |
|---|---|
| 学生端（Web / 小程序 `projectX-mini`） | 未公布考试**从成绩列表消失**；单场详情返回 **404**「该场考试的成绩尚未公布」；趋势/学期/学科对比**不含未公布场次**；天梯**403**；AI 分析**403** |
| 历史数据兼容 | v41 迁移已把存量 `status='closed'` 考试回填 `score_published=1`，升级后历史成绩对学生保持可见，**无需人工干预** |
| 小程序适配要求 | 前端需处理「待公布」状态：列表可提示"老师批改完成后公布"，详情 404 时展示"成绩尚未公布"而非"未找到成绩"（`projectX-mini` 各页 `wx.request` 失败分支需补该文案） |
| 教师/管理员 | **不受影响**：代查（`publishedOnly:false`）、考试详情、天梯均可见未公布成绩（`#246` 权限矩阵照常生效） |

### 变更 B：创建考试强制应考范围 → API 契约变更

| 影响面 | 变化 |
|---|---|
| `POST /api/exams` | 请求体**必须**含 `gradeId` 或 `classId`（至少其一），否则 400 `SCOPE_REQUIRED`「创建考试必须指定应考范围」 |
| 既有前端 | 已同步：考试管理页「新建考试」、答题卡设计器「同步创建考试」两个入口均新增年级/班级必选 |
| 外部集成 | 凡直接调用 `POST /api/exams` 的脚本/第三方集成需补传 `gradeId` 或 `classId`，否则创建失败 |
| 补充 | `PATCH /api/exams/:examId` 现支持补设 `gradeId/classId`（不允许清空）；与显式名单互斥（409） |

## 三、升级操作手册

### 3.1 数据库迁移（自动执行，无需人工）

- **SQLite**：启动时 `schema.sql` + `runMigrations` 自动执行 v47（`exam_participants`）、v48（`exam_participants.source`）。
- **MariaDB**：`getMysqlDb()` 首次连接时 `runMariadbMigrations` 自动执行 v47/v48（幂等，重复列自动忽略）。
- 迁移仅加表/加列，**不修改或删除既有数据**。

### 3.2 存量无范围考试的处置（合入后需管理员操作）

> **§3.2 / §3.3 已由 #326 取代**：无范围、空名单、缺考的考试**现在可以直接公布已有成绩**，不再需要先补范围或先剔名单。下面两条只在你想让「应考名单」视图准确、或想让扫描入库按名单拦人时才需要做。

升级后若存在「未公布且无年级/班级范围」的历史考试（如早期 UI 创建、未补范围），~~**无法直接公布**~~，二选一处理：

1. **设置显式应考名单**（推荐，适合跨班/跨年级联考）：考试管理页 → 行内「应考名单」→ 按班级加载或搜索添加学生 → 保存。
2. **补设范围**：`PATCH /api/exams/:examId`，body `{ "classId": 5 }` 或 `{ "gradeId": 1 }`（需该考试无显式名单）。

> 已公布的存量考试不受影响（幂等早退）。

### 3.3 首次公布前的准备

- ~~考试必须有**应考范围**（年级/班级）或**显式名单**~~ → #326 起无范围也可公布已有成绩；
- ~~班级需已录入学生（空班级无法公布，提示「应考名单为空」）~~ → #326 起空班级不再阻断，但**一条成绩都没有仍 409**「该考试尚无成绩记录（批改未完成）」；
- 名册在首次阅卷/首次公布时**固化快照**——之后调班/转学不影响该场考试口径（如需按新名册，需清空显式名单后重新走班级快照，或人工调整名单）。**这条未变**，快照用于「应考名单」展示与入库身份拦截（`isExamParticipant`），只是不再参与发布判定；
- 新增：写分后是否自动撤回公布，取决于全局设置 `auto_unpublish_on_score_change`（见 §七）。

### 3.4 权限说明

- 公布/撤回/批量公布/名单管理均需 `grade:write`（教师默认拥有）+ 单场 `requireExamAccess` 数据范围（批量经 `getVisibleExamIds` 校验）；
- 批量公布单次上限 **200 场**（超限 400）。

## 六、口径回稳记录（2026-10-04）

> **本节记录的契约已被 §七（2026-10-14，PR #326）再次取代**：第 1～3 条的 409 拒绝已不存在，写分的自动撤回改为管理员开关控制、默认关闭。原文保留是为了让现场能把 2026-10-04～10-14 之间产生的审计数据与当时的口径对上。

PR #296 曾把 §1.3 的发布完整性校验放宽为「有成绩即可公布，不要求名单齐全」，并允许「无范围考试仅校验非空」。该放宽与本文 §3.2/§3.3 相矛盾，且**只改了代码没改文档**，导致同一份说明出现两种口径。2026-10-04 起按主理人决定**回稳到本文原始契约**：

1. 无应考范围且无显式名单 → 409「【完整性校验】未确定应考范围」，**不再有任何退路**；
2. 应考名单为空（空班级 / 名单被清空）→ 409「【完整性校验】应考名单为空」；
3. 名单可知且非空 → 集合校验「应考集合 ⊆ 已评分集合」，缺任何一名应考学生 → 409 并点名缺考者（最多列 5 人）；
4. 单向校验保持：快照之外的多余成绩不阻断发布，也不并入快照；
5. 结考门槛未变：`status IN ('grading','closed')` 均可公布，阅卷中名单齐全就能发。

**已知代价**：现场必须等名单内每人出分才能公布。缺考/辍考学生的正规出路是按 §3.2 用「应考名单」剔除缺考者（显式名单优先于名册快照），或 §3.3 先补范围再按名册剔除；不存在"先发一部分"的选项。

**回归与 CI**：`verify:p1-integrity` 15/0、`verify:p1-scope` 19/0、`verify:p1-readgate` 15/0；三条脚本已于 2026-10-04 注册进 CI 的 `typecheck-and-test` 作业（此前只在本地跑，正是 #296 能悄悄放宽的原因）。MariaDB 侧 `verify:mariadb` 的「发布完整性」一节按同一口径断言（无范围 409 → 名单缺人 409 且能点出缺考者 → 剔除后 200 → 无成绩 409）。

## 七、口径再变更（2026-10-14，PR #326）

PR #296 的放宽被 §六回稳，2026-10-14 的 **PR #326 又回到了「有成绩即可公布」**，但这次是主理人决定、且同步改了脚本、CI 与文档。与 §六的区别：#296 是「悄悄放宽」，#326 是「带着回归断言与全局开关的显式改口径」。以下四条为**现行契约**，与本文 §1.2、§1.3、§3.2、§3.3、§六冲突时**以本节为准**。

### 7.1 公布条件：只要求已有成绩

`assertScoresPublishable`（`src/server/services/examPublication.ts`）现在只有一条断言：`student_scores` 里该场**至少 1 条**成绩，否则 409「该考试尚无成绩记录（批改未完成），无法公布成绩」。

- 无年级/班级范围、无显式名单 → **不再拒绝**（原 409「【完整性校验】未确定应考范围」已删除）；
- 空班级、显式名单被清空 → **不再拒绝**（原「应考名单为空」已删除）；
- 名单可知但缺任何一名应考学生的成绩 → **不再拒绝**（原集合校验与「缺 M 名应考学生成绩」文案及结构化 `missingCount` 字段一并删除）；
- `exam_participants` 快照机制与 `isExamParticipant` 的入库身份拦截（名单外学号拒绝写入本场成绩）**全部保留**，只是退出发布判定；
- 路由侧门槛未变：`status IN ('grading','closed')`、已公布幂等早退、事务内 TOCTOU 复核、批量上限 200 场且任一场不合格整体拒绝不产生部分写入。

### 7.2 写分的自动撤回改为管理员策略

`markScoreMutated`（`src/server/services/examPublishEvents.ts`）先读全局设置 `system_settings.auto_unpublish_on_score_change`：

| 取值 | 行为 | 审计 |
|---|---|---|
| 缺省 / 非 `"1"`（**默认**） | 写分后**保持已公布**，学生立即读到最新成绩 | **不写** `unpublish` 行 |
| `"1"` | 与写分**同一事务**内把整场 `score_published` 打回 0 | 写 `unpublish` + 对应原因文案（`手动改分自动撤回` 等） |

- 该设置是**全局**的，不分考试、不分年级；键不存在即视为关闭，因此**新旧库都无需数据迁移**，`GET /api/system-settings` 对缺失键返回默认 `"0"`；
- 入口：全局设置页 →「成绩变动时自动撤回公布」开关（需 `system:manage`）；`PUT` 只接受 `"0"`/`"1"`，其余 400；
- 覆盖的写分路径不变（`REASON_TEXT` 的 10 个 reason：逐题改分、修改答案、仲裁、网阅提交、赋分重算、赋分禁用、扫描重复学号、扫描重新识别、扫描入库、批量判分入库；扫描历史会话恢复复用 `scanner_save`）；
- **关闭开关不会把已撤回的考试重新公布**，只影响之后的写分；重新公布仍需教师手动操作；
- 撤不撤回都与统计无关：写分一律失效该场 `analysisCache` 并重算排名/赋分（`recomputeExamRankings`）。

### 7.3 对 §二 破坏性变更的影响

变更 A（学生端可见性）**完全不变**：读门仍只认 `score_published=1`，未公布仍是列表消失/详情 404/天梯与 AI 403。变更 B（`POST /api/exams` 强制 `gradeId`/`classId`）**也不变**——范围仍是创建期的硬校验和名单快照的来源，只是不再决定能不能公布。

新增一条对外可见的变化：**公布接口不再提供任何缺考信息**——原先 409 文案里的「缺 M 名应考学生成绩」与结构化 `missingCount` 字段已随集合校验一起删除，而「名单中谁还没出分」这个查询**目前也没有对应的 HTTP 接口**（`listMissingParticipants` 只是服务内函数，被扫描入库路径自用）。`GET /api/exams/:examId/participants` 返回的是应考名单本身（`total` / `students`），其 `missing` 字段含义是**快照里没有账号记录的悬空行数**（`participantCount − students.length`），不是未出分人数。外部集成若要算缺考，需自行拿名单与教师侧成绩列表做差。

### 7.4 为什么默认选择「保持公布」

2026-10-13 教师端「点公布没反应」的现场排查记录过两条叠加的行为：扫描端每次真实入库都会无条件撤回整场公布，教师「点了公布、徽章又变回未公布」；而失败原因只写在被模态遮罩盖住的页脚灰字里，弹框原地不变。无条件撤回与 §六的「全员出分才能公布」叠起来，使现场既不能提前发、发了又留不住。#326 一次解开三处：发布口径交给业务（有成绩即可发）、撤回与否交管理员按场景选、失败原因就地渲染进确认框内。

**代价**：默认态下「已公布」不再等价于「名单齐全」，学生可能先看到部分成绩、后续被补录改写；靠名单推断缺考的教师需改看「应考名单」视图。

### 7.5 现行回归与 CI

| 断言 | 位置 |
|---|---|
| 三种名单形态（无范围/空名单/缺考）均可公布已有成绩 | `verify:p1-integrity`、`verify:p1-scope`（默认态） |
| 策略两态：默认写分保持公布且学生读到新分数；开启后写分即撤回并写审计 | `verify:p1-readgate`（24 项）、`verify:security-critical`（515 项，逐题改分/改答案/仲裁/网阅/赋分全覆盖） |
| 扫描入库、重复学号、重新识别、快照恢复遵循同一策略 | `verify:scanner-batch-results`、`verify:scanner-correction-safety`、`scanner-publish-regression` |
| 同一策略在 MariaDB 方言下的 `markScoreMutated` 返回值与审计行数 | `verify:mariadb`「发布完整性」一节 |
| **两种策略态都进 CI** | `.github/workflows/ci.yml` 在默认态之外，另以 `TEST_AUTO_UNPUBLISH=1` 跑一遍 security-critical / scanner-batch-results / scanner-correction-safety |

断言态的切换方式分两种：`verify:security-critical`、`verify:scanner-batch-results`、`verify:scanner-correction-safety` 以及被 `verify:scanner-review-fixes` 串起来的 `scripts/scanner-publish-regression.ts` 按 `TEST_AUTO_UNPUBLISH=1` 决定期望值；`verify:p1-readgate` 与 `verify:mariadb` 则在脚本内部直接改设置（前者经 `PUT /api/system-settings`、后者直接读写 `system_settings` 行），自己把两态都跑完，不受该环境变量影响。

CI（Node 22）的覆盖分工：`typecheck-and-test` 作业默认态跑 p1 三条 + security-critical，再以 `TEST_AUTO_UNPUBLISH=1` 补跑 security-critical / scanner-batch-results / scanner-correction-safety；MariaDB 作业的两个 scanner 回归只在默认态跑，**开启态的 MariaDB 方言仅由 `verify:mariadb` 里那段 `markScoreMutated` 断言覆盖**。

本机实测记录（SQLite 方言、Node 22.14、隔离临时库，2026-10-14）：`npm run typecheck` 与 `npm run build:web` 通过；`verify:p1-integrity` 15/0、`verify:p1-scope` 19/0、`verify:p1-readgate` 24/0；`verify:security-critical` 在默认态与 `TEST_AUTO_UNPUBLISH=1` 两态下均 515/0。未在本机运行：`verify:mariadb`（无 MariaDB 实例）、三个 scanner 回归；扫描端真实入库与真机 OMR 未验证。
