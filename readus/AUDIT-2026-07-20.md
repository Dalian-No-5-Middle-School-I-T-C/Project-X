# Project-X 全面审核报告（2026-07-20）

> 范围：前端（src/apps/answer-card/client）、后端（src/apps/answer-card/server + src/server）、Electron 壳、构建体系。
> 方法：静态审计 + 三个并行探查代理 + `tsc --noEmit`（结果 EXIT_CODE=0，零编译错误）。
> 结论先行：**有 BUG，但都不是“编译级”硬伤；前端确实“丑且不一致”，根因是设计系统被架空；拆成网页/多界面模式完全可行，且收益很大。**

## 1. BUG 审核

### 1.1 已确认功能缺陷（P0，建议立即修）

- **赋分公式接口缺失 → 功能 404**
  - 前端 `components/AssignedFormulaModal.tsx:39/53` 调用 `GET/PUT /api/exams/:id/assigned-formula`。
  - 后端**没有任何路由注册该路径**（全仓 grep 仅在 `AssignedScoreService` 有 `getAssignedFormula/saveAssignedFormula` 方法，但从未暴露成 HTTP）。
  - 结果：UI 上“赋分公式”必然加载失败、`onSaved` 永不触发。属于典型的“前端已接线、后端未暴露”的功能性 BUG。
  - 修复成本：低（加一个 router 或两行 `app.get/put`，转调已有的 `AssignedScoreService`）。

### 1.2 系统性风险（P1，建议尽快）

- **Express 5 异步未捕获拒绝（请求挂起 / 进程风险）**
  - Express 5 不再自动把 async handler 的 rejected promise 转发给错误处理器。大量 handler 无 `try/catch`：
    - `server/routes/scores.ts`（除两个 ai 接口外几乎全无）
    - `server/routes/score-editing.ts`（5 个 handler 全无）
    - `server/routes/users.ts / classes.ts / teachers.ts / ai-providers.ts / ladder.ts / export-scores.ts`
    - 中间件 `requireExamAccess`、`authMiddleware`、`optionalAuth` 也是 async 直挂。
  - 后果：一旦 DB 抖动/查询抛错，该请求**永远收不到响应**（前端一直转圈）；在 `--unhandled-rejections=throw` 或旧 Node 下会崩进程。
  - 修复：在 `createApp()` 处对 router 做统一 `asyncHandler` 包装，或引入 `express-asyncify`。成本低、收益高。

### 1.3 授权模型（已修正一处误报，但仍有不一致）

- ⚠️ 探查代理曾误报“`exam-groups` 零鉴权”。**实测 `exam-groups.ts:11` 确实有 `router.use(authMiddleware)`**，且有 `req.user!` 保护，并非完全开放。代理此条作废。
- **真实问题：授权策略不统一**
  - 全局 `app.use("/api", optionalAuth)`（index.ts:447）仅“解析身份不拦截”。
  - `cards/exams/analysis` 走 `makeGate(enforceAuth, …)`：**尊重 `PROJECTX_AUTH_ENFORCE`**（关闭时放行，开启时按权限拦截）。
  - 但 `users/classes/teachers/exam-groups/ai-providers` 等用 `authMiddleware`：**无条件要求 token，不读 `enforceAuth`**。
  - 结果：默认“无登录可用”模式下，这批接口反而可能被 token 校验挡住（取决于前端是否总带 token）；开启强制鉴权时，gate 类接口与 middleware 类接口的行为也不一致。属于设计层面的“两套鉴权语义并存”，建议统一为 `enforceAuth` 驱动的网关。

### 1.4 其他中低优先级

| 级别 | 问题 | 位置 |
|---|---|---|
| P2 | 错误响应形状不统一（`{message}` / `{error}` / `{code,…}` 混用），`api-error.ts` 未落地 | 全仓 |
| P2 | `/api/app/health` 注册两次（441 无 try/catch 且遮蔽 613 的死代码） | index.ts:441/613 |

| P3 | 并发竞态：卡片 ID 生成 TOCTOU、后台落库无幂等 | index.ts:713-717 / 1054-1058 |

## 2. 前端风格统一（你说“太丑了”——确实该统一）

### 2.1 诊断：不是没设计系统，是设计系统被架空

- 存在一份相当完整的设计系统：`client/styles.css`（**6601 行 / 829 个类**，含 `:root` 亮色令牌 + `[data-theme="dark"]` 完整暗色主题，品牌色 `--brand:#C00F28` 等）。
- 但 **84%（42/50）的组件在写内联 `style={{}}`**，共 **1015 处内联 style**、**206 处硬编码颜色**（68 处直接在 style 里写死 hex）。即“有人写了 theme，后续开发全 inline 了”。

### 2.2 最刺眼的不一致（按严重度）

1. **同一语义多种硬编码色**：成功绿至少 4 种（`#2E7D32`×15、`#639922`、`#3B6D11`…）；错误红至少 4 种（`#A32D2D`×14、`#e53e3e`、`#E24B4A`…）；灰色 `#555/#666/#888780` 与既有 `--muted` 并存。
2. **模态框 5 种实现 + z-index 通胀**：`100 → 100000 → 100001 → 999999`，靠不断加码盖住上一个（无统一堆叠上下文 / Portal）。`CreateExamGroupModal` 自己写 `position:fixed,zIndex:100000` 绕过 `.modal-overlay`。
3. **分段控件 4 套**：`.mode-toggle`（官方）vs `ScoreFixPage.modeToggleStyle` vs `ExamSelectPage.toggleBtn()` vs `CrossModeBtn`，圆角/内边距/激活态各不相同。
4. **表格双轨**：精致的 `analysis-ranking-table` 等 vs 裸 `<table style={{borderCollapse}}>`（`PermissionManager`、`ExamGroupDetailPage`、`ExportModal` 预览等）。
5. **输入框/按钮圆角内边距无公约**：标准输入框 radius 10/高 38，但模态里到处 radius 4/6/8。
6. **扫描端 `ScannerApp.tsx:26-27` 引用了 `loading-screen`/`loading-spinner` 两个不存在的 CSS 类** → 扫描端加载屏当前完全无样式（附带 bug）。

### 2.3 统一方案（可行，成本可控）

根因是“基类已写好，组件不套用”，所以主要工作是**回流**而非重写：

- **抽 6 个共享组件**（基于现有 CSS 类封装）：`Button` / `Modal`(带 Portal + 固定 z-index 层级) / `SegmentedControl` / `Input` / `Card` / `Table`。
- **内联颜色全部改 `var(--brand)` / `--status-ok` / `--text-secondary` 等令牌**；建一份 `theme.ts` 让 TS 侧也能引用，避免“同一文件混用 var 与 hex”。
- **统一 z-index 阶梯**（如 modal=1000、toast=1100、lightbox=1200），删掉 999999 这类魔法数。
- **修 ScannerApp 缺失的 loading 类**；合并重复的深色灯箱（ScoreFixPage 与 StudentScoreDetail 几乎一致的代码）。
- **工作量**：约 42 个组件需逐个回流，但多为机械替换；建议按“壳层 → 高频页面（设计/阅卷/分析）→ 管理类页面”分三批。整体属于中工作量、低风险。

## 3. 拆成网页模式（每开一个功能都新开一个界面）

### 3.1 现状（探查结论）

- **无路由库**：客户端没有 `react-router`，所有功能靠 `App.tsx` 里的 `mode` 状态切换（`AppMode = design|exam-manage|grading|analysis|scores|account|…`）。
- **全部挂载 + CSS 隐藏**：9 个功能 `main-grid` 同时存在于 DOM，靠 `.hidden-panel{display:none}` 显隐。切换只是去掉当前 div 的 hidden-panel。
- **App.tsx 是 2000+ 行巨石组件**，内含数十个 `useState`，各功能强耦合。
- **无法深链 / 刷新即丢状态 / 不能开新标签直达某功能**（如 `/analysis/123`）。
- **Electron 仅打包 Scanner 端**（`ScannerApp`），教师功能只走 web 构建（`dist/web/`）。所以“新开界面”在你们的实际部署里＝**浏览器新标签页/窗口**，不是 Electron 多窗口。

### 3.2 方案对比

| 方案 | 做法 | 优劣 |
|---|---|---|
| **A. 引入 react-router（推荐）** | 每个功能 = 真实路由（`/design` `/grading` `/analysis/:examId` …）；共享壳（TopBar/StatusBar）抽成 Layout。 | 改动中等；天然支持深链 + 刷新保留 + **`window.open('/grading')` 即可“每功能新开一个浏览器界面”**；最贴合“网页模式”。 |
| B. Electron 多窗口 | 每个功能 `new BrowserWindow` / BrowserView | 仅当你要把教师功能也塞进桌面端才有意义；当前 Electron 只跑 Scanner，收益低、改造大。 |
| C. 仅加“弹出”按钮 | 保留 SPA，给每个功能加 `window.open` 到独立迷你页 | 最小改动，但每个迷你页要重复实现壳，易漂移；不解决深链。 |

### 3.3 推荐路线（网页模式 = A）

1. **阶段 0（先修 BUG）**：补 `assigned-formula` 路由 + 全局 async 包装 + 统一鉴权语义。
2. **阶段 1（统一风格）**：抽共享组件、回流内联样式、修 z-index 与 ScannerApp loading 类（§2.3）。视觉收益最大、风险最低，可独立交付。
3. **阶段 2（路由化）**：引入 `react-router-dom`；把 `App.tsx` 拆为 `Layout`（壳）+ 各 `Route` 页面组件；`mode` 状态改为 URL。完成后“每功能新开界面”= 在功能 Tab 上右键/`window.open` 打开对应路由即可。
4. **阶段 3（可选，桌面体验）**：若需要原生多窗口，再在 Electron 端用 BrowserView 加载各路由。
