## 修复计划：PR #201 演示数据 P0 安全阻断问题

### 根因
`DemoDataService.ts` 的 `cleanupDemoData()` 使用**硬编码的学号、答题卡 ID、用户名和班级/年级名称**来识别并删除演示数据。如果学校真实数据恰好匹配这些固定值（如真实学生学号 20260101、真实答题卡 ID 88000001、真实教师用户名 demo-teacher），点击「导入演示数据」或「清除演示数据」会**误删真实账号和数据**，与前端承诺的「不会覆盖现有数据 / 不影响真实数据」直接冲突。

### 修复方案：添加可靠的演示数据归属标记

由于数据库目前没有任何 `is_demo`/`source` 列，现有 4 个表（`users`、`answer_cards`、`classes`、`grades`）完全依赖命名/ID 匹配。修复需：
1. 给 4 个表添加 `is_demo INTEGER DEFAULT 0` 列；
2. 创建演示数据时标记 `is_demo = 1`；
3. 清理时按 `is_demo = 1` 删除，不再依赖硬编码值。

`exams` 和 `exam_groups` 仍用 `name LIKE '演示-%'` 识别（前缀独特，且审查未列其为问题），保持不变。

---

### 实施步骤

#### Step 1 — 数据库迁移（Migration 28）
在 `src/server/db/migrations.ts` 中新增 version 28 迁移，为 4 个表添加列：
```sql
ALTER TABLE users        ADD COLUMN is_demo INTEGER DEFAULT 0;
ALTER TABLE answer_cards ADD COLUMN is_demo INTEGER DEFAULT 0;
ALTER TABLE classes      ADD COLUMN is_demo INTEGER DEFAULT 0;
ALTER TABLE grades       ADD COLUMN is_demo INTEGER DEFAULT 0;
```
使用现有的 `addColumnIfMissing()` 辅助函数，确保幂等。

#### Step 2 — 同步 schema.sql
在 `src/server/db/schema.sql` 的 `CREATE TABLE` 语句中同步添加 `is_demo INTEGER DEFAULT 0`，保证新库结构一致。

#### Step 3 — 修改创建逻辑（`DemoDataService.ts`）
在 `seedDemoData()` 中，插入以下记录时显式设置 `is_demo = 1`：
- **学生用户**（16 名）：`INSERT INTO users (... , is_demo) VALUES (... , 1)`
- **教师用户**（demo-teacher、demo-teacher-2）
- **答题卡**（88000001~88000008、88000999）
- **班级**（演示1班、演示2班）
- **年级**（高一(演示)）

> 注意：班级/年级的创建通过 `ClassRepository` 进行，若 Repository 未暴露 `is_demo` 参数，可直接在 `seedDemoData()` 中用 `db.prepare()` 执行 `UPDATE classes SET is_demo = 1 WHERE name IN (...)` 作为后处理。

#### Step 4 — 修改清理逻辑（`DemoDataService.ts`）
将 `cleanupDemoData()` 中的硬编码删除替换为按归属标记删除：

| 原逻辑（危险） | 新逻辑（安全） |
|---|---|
| `DELETE FROM answer_cards WHERE id = '88000999'` 以及循环删 `88000001`~`88000008` | `DELETE FROM answer_cards WHERE is_demo = 1` |
| `DELETE FROM users WHERE student_number IN (20260101..20260116)` | `DELETE FROM users WHERE is_demo = 1 AND role_id = ?(学生角色)` |
| `DELETE FROM users WHERE username = 'demo-teacher'` / `'demo-teacher-2'` | 合并入上一条：`DELETE FROM users WHERE is_demo = 1`（配合角色/用户名双重确认可选） |
| `DELETE FROM classes WHERE name IN ('演示1班','演示2班')` | `DELETE FROM classes WHERE is_demo = 1` |
| `DELETE FROM grades WHERE name = '高一(演示)'` | `DELETE FROM grades WHERE is_demo = 1` |

删除顺序保持现有逻辑（先关联子表，再父表；classes 先于 grades），仅将 `WHERE` 条件从固定值改为 `is_demo = 1`。

#### Step 5 — 验证
执行以下命令确保修改无回归：
1. `npm run typecheck` — 零类型错误
2. `npm run verify:auth` — 54/54 通过
3. `npm run verify:security-critical` — 42/42 通过
4. 手动确认迁移脚本在新库和已有库上均能正常升级

### 风险与边界
- **外键顺序**：`classes.grade_id → grades.id` 无 CASCADE（已知），删除顺序必须保持 `classes` 先于 `grades`，现有逻辑已满足。
- **已有演示数据**：对于在旧版本（无 `is_demo` 列）已导入演示数据的数据库，Migration 28 会把所有历史记录的 `is_demo` 设为 `0`。此时若用户点击「清除演示数据」，这些旧演示数据不会被清理（因为 `is_demo = 0`）。这是**可接受的安全行为**——宁可漏清旧演示数据，也不能误删真实数据。用户可重新「导入演示数据」（会先执行清理，但按新标记清理；旧数据因无标记而保留），或手动清理。
- **最小修改**：不涉及 `exams`/`exam_groups`/`exam_group_items`/`exam_group_members` 等已有安全前缀识别的表，改动范围最小化。
